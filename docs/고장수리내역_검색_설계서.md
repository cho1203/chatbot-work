# 고장수리내역 검색 기능 설계서

| 항목 | 내용 |
|---|---|
| 대상 | 삼광 설비 고장수리내역 (엑셀, 시트 약 40개) |
| 범위 | 사용자 질의를 받아 유사한 수리 사례를 최대 3건 찾고, 원본을 PDF로 보여줌 |
| 문서 목적 | 회의(10/14) 피드백을 반영한 수정 설계. 이 문서를 기준으로 바로 코드 작성 단계에 들어감 |
| 상태 | 설계 확정 대기 (목요일 오후 미팅에서 검토 예정) |

---

## 1. 설계 변경 요약

### 1.1 기존 설계

```
질의 → 식별자 4개(장비명·모델명·규격사양·현장명) 키워드 일치 → (일치 시) 해당 설비 사례만 대상
     → BGE 유사도 → 최종 1개 → PDF
```

### 1.2 기존 설계의 문제점 (회의 피드백)

| # | 문제 | 영향 |
|---|---|---|
| 1 | 질의에서 식별자가 검출되지 않으면 검색 자체가 불가 | 검색 누락 |
| 2 | 질의가 길어지면 키워드 기반 검색 성능이 떨어짐 | 정확도 저하 |
| 3 | 40개 데이터 기준으로 하드코딩된 구조라 1만~10만 건으로 늘어나면 대응 불가 | 확장성 없음 |
| 4 | 고장수리내역은 정해진 양식이 없어 키워드로 찾기 어려움 | 정확도 저하 |
| 5 | 라벨링을 유지하려면 입력 양식을 강제해야 함 | 사용자 불편 |
| 6 | 정규표현식 기반 식별자 추출은 다른 고객사(MVBot 확장)에서 쓸 수 없음 | 확장성 없음 |
| 7 | 유사도가 임계값보다 낮을 때의 **후처리 로직이 없음** | 결과 없음 처리 불가 |
| 8 | 결과가 1개뿐이라 참고할 비슷한 사례를 볼 수 없음 | 활용도 저하 |
| 9 | 식별자를 4개만 써서 작업명·부품·날짜 등 양식의 다른 항목을 검색에 활용하지 못함 | 정보 손실 |

### 1.3 변경된 설계

```
질의 → [질의 분석: LLM] → 식별자 JSON + 날짜 조건 + 의미 질의
                         ├─ 식별자 검색 (PostgreSQL 일치/유사)
                         └─ 의미 검색   (pgvector, BGE-M3)
      → [판단] 임계값 이상 상위 3개 / 미달 시 후처리(식별자 2개 이상 일치 목록) / 없음
      → 챗봇에 목록 표시 → 클릭 시 원본 시트 PDF
```

| 항목 | 기존 | 변경 |
|---|---|---|
| 첫 단계 | 바로 키워드 검색 | **질의 분석**(LLM, JSON 추출) |
| 추출 항목 | 식별자 4개 | **양식 전체 항목 17개**를 추출·저장 (3.2절) |
| 식별자 추출 | 키워드 매칭 | LLM 추출 + 정규화 |
| 검색 구조 | 식별자로 거른 뒤 의미 검색 (종속) | 식별자 검색과 의미 검색을 **독립 실행** |
| 날짜 | 미사용 | 보고일자·고장발생일·작업일시로 **기간 필터** |
| 결과 개수 | 1개 | **최대 3개** |
| 임계값 미달 | 처리 없음 | **후처리**: 식별자 2개 이상 일치 목록 표시 |
| 결과 없음 | 정의 없음 | "찾지 못했습니다" (오답 노출 금지) |
| 표시 | PDF | 목록 → 클릭 시 원본 시트 PDF |

> 각 변경 사항을 왜 넣었는지, 그래서 챗봇이 어떻게 좋아지는지는 **9장 설계 근거**에 정리했다.

### 1.4 기능 성격

- 이 기능은 RAG 전체가 아니라 **Retriever(R)만** 사용한다. 증강·생성은 하지 않는다.
- 따라서 정확도를 결정하는 핵심은 **질의를 어떻게 처리하느냐**다.
- 임베딩 모델 자체는 수정할 수 없다. 성능이 부족하면 모델을 교체한다.

## 2. 전체 구조

### 2.1 처리 흐름

```
[오프라인: 적재]
엑셀 ─► 시트 분리 ─► 양식 항목 17개 추출 ─► 정규화(식별자) / 날짜 파싱
                 └─► 시트별 PDF 변환
                                   ─► 본문 임베딩(BGE-M3) ─► PostgreSQL(repair_cases, repair_parts)

[온라인: 검색]
사용자 질의
  │
  ▼
① 질의 분석 (LLM) ─► {식별자들, 날짜 조건, semantic_query}
  │
  ├─► ② 식별자 검색 (pg_trgm, 날짜 필터)  ─► 같은 설비 후보 집합 S
  │
  ▼
③ 의미 검색 (pgvector, 날짜 필터) — 2단계
   ├ 1차: S 안에서만 의미 검색   → score ≥ THRESHOLD → [같은 설비] 그룹
   └ 2차: 3개가 안 차면 전체에서 의미 검색 (1차 결과 제외)
                                → score ≥ THRESHOLD → [다른 설비] 그룹으로 채움
  │
  ▼
④ 판단
   ├ 1차·2차 결과 존재            → 최대 3개, 같은 설비 우선 (mode=semantic)
   ├ 없음 & match_count ≥ 2 존재 → 일치 순 최대 3개        (mode=identifier_fallback)
   └ 둘 다 없음                  → 빈 목록 + 메시지       (mode=none)
  │
  ▼
⑤ 챗봇 카드 목록 표시 ─► 클릭 ─► /cases/{case_id}/pdf
```

## 3. 데이터 설계

### 3.1 원본 데이터 처리 방침

- 원본은 엑셀로 유지한다. 시트 1개를 수리 사례 1건으로 본다.
- 검색용 텍스트는 엑셀에서 추출한다. **사용자에게 보여주는 것은 원본 시트를 PDF로 변환한 것**이다.
- 이유: 엑셀 텍스트를 그대로 보여주면 병합셀, 특수공백, 빈칸 등으로 깨지거나 그림이 빠질 수 있다.
  → 근거는 `scripts/check_excel_text.py` 리포트로 확인한다 (6장 참고).
- 시트별 읽기는 라이브러리가 지원하므로 엑셀 파일을 시트별로 따로 쪼개지 않는다.

### 3.2 추출 항목 (고장수리내역 양식 전체)

양식의 모든 항목을 추출해 저장하고, 항목 성격에 따라 **식별자 / 날짜 / 본문 / 부품** 4가지 용도로 나눈다.

| # | 양식 항목 | 컬럼명 | 타입 | 용도 |
|---|---|---|---|---|
| 1 | 보고일자 | report_date | DATE | 날짜 필터 |
| 2 | 보고자 | reporter | TEXT | 식별자 |
| 3 | 장비개요 | equipment_overview | TEXT | 본문 |
| 4 | 장비명 | equipment | TEXT | 식별자 |
| 5 | 모델명 | model | TEXT | 식별자 |
| 6 | 규격/사양 | spec | TEXT | 식별자 |
| 7 | 작업명 | work_name | TEXT | 식별자 + 본문 |
| 8 | 현장명 | site | TEXT | 식별자 |
| 9 | 고장발생일 | failure_date | DATE | 날짜 필터 |
| 10 | 작업일시 | work_datetime | TIMESTAMP | 날짜 필터 |
| 11 | 고장현상 및 고장원인 | symptom_cause | TEXT | 본문 |
| 12 | 조치내용 및 대책방안 | action_plan | TEXT | 본문 |
| 13 | 작업구분 | work_type | TEXT | 식별자 |
| 14 | 사용부품명 | part_name | TEXT | 식별자 (부품 테이블) |
| 15 | 규격 (부품) | part_spec | TEXT | 부품 정보 |
| 16 | 수량 (부품) | part_qty | NUMERIC | 부품 정보 |
| 17 | 작업내용 | work_detail | TEXT | 본문 |

- **모델명**은 양식에 두 번 나온다. 같은 값이면 하나로 저장한다. 위치마다 의미가 다르면(예: 장비 모델과 부품 모델) 두 번째를 `model_2`로 따로 저장한다. → 샘플 시트로 확인 후 확정 (8장 #7)
- **사용부품명·규격·수량**은 한 사례에 여러 줄이 있을 수 있으므로 별도 테이블 `repair_parts`에 행 단위로 저장한다.
- **본문(`full_text`)** = 장비개요 + 작업명 + 고장현상 및 고장원인 + 조치내용 및 대책방안 + 작업내용
  - 작업명은 "유압 실린더 패킹 교체"처럼 의미를 담고 있어 식별자와 본문 양쪽에 모두 쓴다.
  - 그 외 식별자(장비명, 모델명 등)는 본문에 넣지 않는다. 식별자와 의미를 **독립적으로** 검색하기 위해서다.
- 항목 값은 시트 안의 라벨 셀(예: "장비명" 셀의 오른쪽이나 아래 셀)에서 읽는다. 라벨 위치는 샘플 시트로 확인한 뒤 확정한다.
- 빈 항목은 null로 저장한다. 항목이 비어 있어도 사례 적재는 실패하지 않아야 한다.

### 3.3 정규화 규칙

**식별자 (텍스트)**
```python
def norm(s: str | None) -> str:
    # 전각→반각(NFKC), 공백·하이픈·언더스코어 제거, 대문자화
    return re.sub(r"[\s\-_]", "", unicodedata.normalize("NFKC", s or "")).upper()
# "mc 4", "MC-4", "Mc4" → "MC4"
```

**날짜**
- `2026.10.14`, `2026-10-14`, `26/10/14`, 엑셀 날짜 일련번호 등을 모두 `DATE` / `TIMESTAMP`로 변환한다.
- 파싱에 실패하면 null로 두고, 원문은 `*_raw` 컬럼에 남긴다.

**수량**
- `2EA`, `2 개` 같은 값은 숫자(2)만 `part_qty`에 저장하고, 원문은 `part_qty_raw`에 남긴다.

### 3.4 테이블

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE repair_cases (
  case_id             TEXT PRIMARY KEY,
  source_file         TEXT,
  sheet_name          TEXT,
  pdf_path            TEXT,

  -- 날짜
  report_date         DATE,
  failure_date        DATE,
  work_datetime       TIMESTAMP,
  report_date_raw     TEXT,
  failure_date_raw    TEXT,
  work_datetime_raw   TEXT,

  -- 식별자 (원본)
  reporter            TEXT,
  equipment           TEXT,
  model               TEXT,
  spec                TEXT,
  work_name           TEXT,
  site                TEXT,
  work_type           TEXT,

  -- 식별자 (정규화)
  reporter_n          TEXT,
  equipment_n         TEXT,
  model_n             TEXT,
  spec_n              TEXT,
  work_name_n         TEXT,
  site_n              TEXT,
  work_type_n         TEXT,

  -- 본문
  equipment_overview  TEXT,
  symptom_cause       TEXT,
  action_plan         TEXT,
  work_detail         TEXT,
  full_text           TEXT,
  embedding           vector(1024),

  created_at          TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE repair_parts (
  id            BIGSERIAL PRIMARY KEY,
  case_id       TEXT REFERENCES repair_cases(case_id) ON DELETE CASCADE,
  part_name     TEXT,
  part_name_n   TEXT,
  part_spec     TEXT,
  part_qty      NUMERIC,
  part_qty_raw  TEXT
);

-- 의미 검색
CREATE INDEX ON repair_cases USING hnsw (embedding vector_cosine_ops);
-- 식별자 검색
CREATE INDEX ON repair_cases USING gin (equipment_n gin_trgm_ops);
CREATE INDEX ON repair_cases USING gin (model_n     gin_trgm_ops);
CREATE INDEX ON repair_cases USING gin (spec_n      gin_trgm_ops);
CREATE INDEX ON repair_cases USING gin (work_name_n gin_trgm_ops);
CREATE INDEX ON repair_cases USING gin (site_n      gin_trgm_ops);
CREATE INDEX ON repair_cases (work_type_n);
CREATE INDEX ON repair_cases (reporter_n);
CREATE INDEX ON repair_parts USING gin (part_name_n gin_trgm_ops);
-- 날짜 필터
CREATE INDEX ON repair_cases (failure_date);
CREATE INDEX ON repair_cases (report_date);
```

- 식별자 검색은 별도 벡터 없이 PostgreSQL의 정확 일치 + pg_trgm 유사도로 처리한다.
  (회의에서 "PostgreSQL 일치 검색 vs pgvector"로 논의된 부분에 대한 제안안)
- 신규 데이터는 `upsert_case(record)` 함수 하나로 두 테이블에 함께 적재한다. 데이터가 늘어나도 구조 변경이 필요 없다.

## 4. 모듈 상세 설계

### 4.1 질의 분석 — `search/query_parser.py`

```python
def parse_query(query: str) -> ParsedQuery
```

| 항목 | 내용 |
|---|---|
| 입력 | 사용자 질의 원문 |
| 출력 | 아래 JSON (식별자는 정규화, 날짜는 ISO 형식으로 반환) |
| 모델 설정 | temperature 0, few-shot 예시 3~4개 |
| 실패 처리 | JSON 파싱 실패 시 1회 재시도 → 그래도 실패하면 식별자와 날짜는 모두 null, semantic_query = 원문 |

```json
{
  "identifiers": {
    "reporter": "string | null",
    "equipment": "string | null",
    "model": "string | null",
    "spec": "string | null",
    "work_name": "string | null",
    "site": "string | null",
    "work_type": "string | null",
    "part_name": "string | null"
  },
  "date_filter": {
    "field": "failure_date | report_date | work_datetime | null",
    "from": "YYYY-MM-DD | null",
    "to": "YYYY-MM-DD | null"
  },
  "semantic_query": "식별자와 날짜를 뺀 증상·원인·조치 관련 설명",
  "raw_query": "원문"
}
```

**시스템 프롬프트**
> 너는 설비 고장 질의 분석기다. 사용자 질의에서 보고자, 장비명, 모델명, 규격사양, 작업명, 현장명, 작업구분, 사용부품명을 추출하라. "지난달", "올해 3월" 같은 기간 표현은 오늘 날짜(`{today}`) 기준으로 date_filter의 from/to로 바꿔라. 날짜가 고장 발생 시점이면 failure_date, 보고 시점이면 report_date, 작업 시점이면 work_datetime으로 지정하라. 질의에 명시되지 않은 항목은 null로 둔다. 추측 금지. semantic_query에는 고장 현상, 원인, 조치에 관한 내용만 간결하게 남겨라. JSON만 출력하라.

**예시**
- 입력: "지난달 2공장 mc 4 프레스에서 기름이 아래로 샜던 거 패킹 뭐로 갈았어?"
- 출력:
  ```json
  {"identifiers":{"equipment":"프레스","model":"MC4","site":"2공장","part_name":"패킹",
                  "reporter":null,"spec":null,"work_name":null,"work_type":null},
   "date_filter":{"field":"failure_date","from":"2026-09-01","to":"2026-09-30"},
   "semantic_query":"프레스 하부 기름 누유 패킹 교체"}
  ```

### 4.2 식별자 검색 — `search/retriever.py`

```python
def identifier_search(parsed: ParsedQuery, k: int = 10) -> list[IdHit]
# IdHit = (case_id, match_count, matched_fields)
```

- 대상 식별자: 보고자, 장비명, 모델명, 규격/사양, 작업명, 현장명, 작업구분, 사용부품명 (8개)
- null이 아닌 식별자만 조건에 넣는다(쿼리는 동적으로 조립).
- 필드별 일치 판정 방식:

| 필드 | 판정 |
|---|---|
| 장비명, 모델명, 규격/사양, 작업명, 현장명 | 정확 일치 또는 `similarity ≥ TRGM_MIN` |
| 작업구분, 보고자 | 정확 일치 (값 종류가 적고 짧음) |
| 사용부품명 | `repair_parts`에서 하나라도 `similarity ≥ TRGM_MIN`이면 일치 |

- 날짜 조건이 있으면 `WHERE`에 기간 필터를 추가한다.
- `match_count` 내림차순으로 정렬한다.

```sql
-- 예: model, site, part_name + 고장발생일 기간이 들어온 경우
SELECT c.case_id,
  ( CASE WHEN c.model_n = %(m)s OR similarity(c.model_n, %(m)s) >= 0.6 THEN 1 ELSE 0 END
  + CASE WHEN c.site_n  = %(s)s OR similarity(c.site_n,  %(s)s) >= 0.6 THEN 1 ELSE 0 END
  + CASE WHEN EXISTS (SELECT 1 FROM repair_parts p
                      WHERE p.case_id = c.case_id
                        AND similarity(p.part_name_n, %(p)s) >= 0.6) THEN 1 ELSE 0 END
  ) AS match_count
FROM repair_cases c
WHERE c.failure_date BETWEEN %(from)s AND %(to)s
ORDER BY match_count DESC
LIMIT %(k)s;
```

### 4.3 의미 검색 — `search/retriever.py`

```python
def semantic_search(
    semantic_query: str,
    date_filter: DateFilter | None,
    include_ids: list[str] | None = None,   # 1차: 같은 설비 후보 S 안에서만
    exclude_ids: list[str] | None = None,   # 2차: 1차 결과 제외하고 전체에서
    k: int = 10,
) -> list[SemHit]
# SemHit = (case_id, score)   score = 코사인 유사도
```

```sql
SELECT case_id, 1 - (embedding <=> %(qvec)s) AS score
FROM repair_cases
WHERE (%(from)s IS NULL OR failure_date >= %(from)s)
  AND (%(to)s   IS NULL OR failure_date <= %(to)s)
  AND (%(include_ids)s IS NULL OR case_id = ANY(%(include_ids)s))
  AND (%(exclude_ids)s IS NULL OR NOT (case_id = ANY(%(exclude_ids)s)))
ORDER BY embedding <=> %(qvec)s
LIMIT %(k)s;
```

- 같은 함수를 두 번 호출한다. 1차는 `include_ids=S`, 2차는 `exclude_ids=1차 결과`.
- 식별자가 하나도 추출되지 않으면 S가 비어 있으므로 1차를 건너뛰고 2차(전체 검색)만 수행한다. 즉 **식별자가 없어도 의미 검색은 항상 수행된다.**
- 날짜 필터는 두 검색에 똑같이 적용한다.

### 4.4 판단 및 후처리 — `search/pipeline.py`

```python
def search_repair(query: str) -> SearchResult
```

**해결하려는 상황: 식별자는 맞는데 내용이 다른 경우**

> 예: "MC4 2공장 모터에서 타는 냄새 나요"
> - MC4·2공장 사례는 있지만 내용은 "누유 수리" → 식별자만 맞고 증상이 다름
> - 다른 모델(MC6)에 "모터 과열·탄 냄새" 사례가 있음 → 증상은 맞지만 설비가 다름
>
> 사용자에게 가장 좋은 결과는 **"같은 설비 + 비슷한 증상"**, 그다음은 **"다른 설비 + 비슷한 증상"** 이다.
> 식별자만 맞고 증상이 다른 사례는 최후의 참고 자료다.

**처리 순서**

```python
def search_repair(query):
    parsed = parse_query(query)

    # ② 같은 설비 후보 집합 S: CORE_IDS 중 1개 이상 일치한 사례
    id_hits = identifier_search(parsed)
    S = [h.case_id for h in id_hits if h.matched_fields & CORE_IDS]

    # ③-1차: 같은 설비 안에서 의미 검색
    same = []
    if S:
        same = [h for h in semantic_search(parsed.semantic_query, parsed.date_filter, include_ids=S)
                if h.score >= THRESHOLD]

    # ③-2차: 3개가 안 차면 전체에서 의미 검색으로 채움
    other = []
    if len(same) < TOP_N:
        other = [h for h in semantic_search(parsed.semantic_query, parsed.date_filter,
                                            exclude_ids=[h.case_id for h in same])
                 if h.score >= THRESHOLD]

    results = (tag(same, "same_equipment") + tag(other, "other_equipment"))[:TOP_N]

    # ④ 판단
    if results:
        return build("semantic", results, message=msg_for(S, same, other))
    fallback = [h for h in id_hits
                if h.match_count >= MIN_ID_MATCH and h.matched_fields & CORE_IDS][:TOP_N]
    if fallback:
        return build("identifier_fallback", fallback, message=FALLBACK_MSG)
    return build("none", [], message=NONE_MSG)
```

**판단 규칙**

| 순서 | 조건 | 결과 | mode / group |
|---|---|---|---|
| 1 | 같은 설비(S) 안에서 score ≥ THRESHOLD | 우선 표시 | `semantic` / `same_equipment` |
| 2 | 1이 3개 미만이면 전체에서 score ≥ THRESHOLD (1 제외) | 남은 자리 채움 | `semantic` / `other_equipment` |
| 3 | 1, 2 모두 없고, match_count ≥ MIN_ID_MATCH (CORE_IDS 포함) | 일치 개수 순 최대 3개 | `identifier_fallback` |
| 4 | 모두 없음 | 빈 목록 + "유사한 수리 사례를 찾지 못했습니다" | `none` |
| 공통 | score ≥ HIGHLIGHT | `highlight = true` | |

**안내 문구 (`msg_for`)**

| 상황 | 문구 |
|---|---|
| 같은 설비 결과만 있음 | (문구 없음) |
| 같은 설비 + 다른 설비 섞임 | "같은 설비 사례 N건과 다른 설비의 비슷한 증상 사례 M건입니다" |
| S는 있는데 같은 설비 결과가 없고 다른 설비만 있음 | "{모델명}의 수리 이력은 있지만 비슷한 증상은 없습니다. 다른 설비의 비슷한 증상 사례입니다" |
| 식별자 자체가 없어서 S가 비어 있음 | (문구 없음, 전체 검색 결과만 표시) |

**핵심 원칙**

- **임계값은 1차·2차 모두 같은 값을, 의미 점수(score) 그대로** 적용한다. 같은 설비라는 이유로 기준을 낮추거나 가산점을 더하지 않는다.
  → 식별자만 맞고 내용이 다른 사례가 의미 검색 결과로 섞여 들어오는 것을 막는다 (G1).
- 식별자만 맞는 사례는 3번(후처리)에서만, 안내 문구와 함께 보여준다. 이것이 회의에서 정한 **후처리 로직**이다.
- 4번은 고장수리내역 특성상 **틀린 결과를 보여주지 않기 위한** 규칙이다.
- 식별자가 8개로 늘었기 때문에, 보고자·작업구분처럼 변별력이 낮은 항목만 일치해도 2개가 채워질 수 있다. 그래서 S와 후처리 모두 장비명·모델명·현장명·사용부품명 중 최소 1개가 일치해야 한다는 `CORE_IDS` 조건을 둔다.

**반환 형식**

```json
{
  "mode": "semantic | identifier_fallback | none",
  "message": "string | null",
  "results": [
    {
      "case_id": "S07",
      "title": "유압프레스 MC4 / 2공장 — 실린더 패킹 교체",
```

## 6. 검증 계획

### 6.1 엑셀 텍스트 깨짐 및 양식 검증 — `scripts/check_excel_text.py`

- 시트마다 병합셀 개수, 빈 셀 비율, 줄바꿈과 특수공백(`\xa0`, `　`)이 들어간 셀, 이미지 개수와 위치를 리포트한다.
- **양식 항목 17개의 라벨 위치가 모든 시트에서 같은지**, 항목별로 비어 있는 비율이 얼마인지도 함께 리포트한다.
- 목적: "텍스트 대신 PDF로 보여준다"는 결정의 근거를 확보하고, 추출 규칙을 확정한다.

### 6.2 검색 평가 및 임계값 결정 — `scripts/eval.py`

- 평가 질의 약 30개를 만든다. 형식: `{query, expected_case_ids, type}`
  - type: `short` / `long` / `no_identifier` / `typo` / `date` / `part` / `no_answer`
- THRESHOLD를 0.30~0.80까지 0.05 단위로 바꿔 가며 다음 지표를 측정한다.

| 지표 | 정의 |
|---|---|
| Recall@3 | 정답 사례가 상위 3개 안에 있는 비율 |
| 오답 노출률 | 정답이 아닌 사례를 보여준 비율 (정답이 없는 질의에 결과를 보여준 경우 포함) |
| mode 비율 | semantic / fallback / none 비율 |

- **선택 기준: 오답 노출률이 0에 가까운 범위에서 Recall@3이 가장 높은 값**
- `long`, `no_identifier` 유형의 Recall은 따로 측정한다. 기존 키워드 방식보다 나아졌다는 근거로 쓴다.
- 참고: BGE-M3는 관련 없는 문장끼리도 코사인 점수가 비교적 높게 나올 수 있으므로, 회의에서 예로 든 0.5를 그대로 쓰지 않고 측정해서 정한다.

### 6.3 완료 기준

## 9. 설계 근거 — 왜 이렇게 하면 더 좋은 챗봇이 되는가

이 장은 이번에 추가·변경한 항목마다 **무엇을 / 왜(목적) / 근거(어떤 문제를 해결하는지) / 효과(사용자가 체감하는 변화)** 를 정리한다.
"근거"의 번호는 1.2절 문제점 번호를 가리킨다.

### 9.1 핵심 목표 3가지

모든 설계 결정은 다음 세 가지 목표 중 하나 이상을 위해 들어갔다.

| 목표 | 의미 | 왜 중요한가 |
|---|---|---|
| **G1. 틀린 결과를 보여주지 않는다** | 확신이 없으면 보여주지 않거나, 왜 보여주는지 밝힌다 | 고장수리내역은 현장 작업자가 실제 수리에 참고한다. 잘못된 사례는 사고와 설비 손상으로 이어질 수 있다 |
| **G2. 어떻게 물어봐도 찾는다** | 짧은 질문, 긴 질문, 오타, 모델명 없는 질문도 처리한다 | 현장 사용자는 정해진 형식으로 묻지 않는다 |
| **G3. 데이터가 늘어도 그대로 쓴다** | 40건이 10만 건이 되어도, 다른 고객사로 확장해도 구조를 바꾸지 않는다 | 사용자 입력으로 데이터가 계속 쌓이고, MVBot 확장도 고려해야 한다 |

### 9.2 데이터 항목별 근거

#### (1) 양식 전체 항목 17개 추출 (기존 4개 → 17개)

| 구분 | 내용 |
|---|---|
| 무엇을 | 고장수리내역 양식의 모든 항목을 추출해 DB에 저장한다 |
| 목적 | 양식에 이미 적혀 있는 정보를 버리지 않고 검색과 표시에 모두 활용한다 |
| 근거 | 문제 9. 4개만 쓰면 "어떤 부품을 썼는지", "언제 고장났는지", "어떤 작업이었는지" 같은 질문에 답할 수 없다 |
| 효과 | 답할 수 있는 질문의 종류가 늘어난다 (9.4절 표 참고). 나중에 통계나 대시보드를 만들 때도 같은 데이터를 다시 쓸 수 있다 |
| 목표 | G2, G3 |

#### (2) 식별자 확대: 작업명, 작업구분, 사용부품명, 보고자 추가

| 항목 | 목적 | 이런 질문에 답할 수 있다 |
|---|---|---|
| 작업명 | 수리 작업 자체로 찾는다 | "실린더 패킹 교체 작업 사례 보여줘" |
| 작업구분 | 긴급수리, 정기점검 등 작업 성격으로 좁힌다 | "긴급수리였던 것만 보여줘" |
| 사용부품명 | 부품 기준으로 찾는다. 현장에서 가장 많이 나올 질문 유형 중 하나다 | "오링 교체한 이력 있어?" |
| 보고자 | 담당자 기준으로 찾는다 | "김OO 님이 보고한 건" (사용 여부는 미결 #9) |

- 근거: 문제 1. 식별자 종류가 많을수록 질의에서 최소 하나라도 잡힐 확률이 올라간다.
- 목표: G2

#### (3) 날짜 3종: 보고일자, 고장발생일, 작업일시

| 구분 | 내용 |
|---|---|
| 무엇을 | 날짜를 DATE/TIMESTAMP 타입으로 정규화하고, 질의의 기간 표현을 필터로 바꾼다 |
| 목적 | "언제"를 조건으로 검색 범위를 좁힌다 |
| 근거 | 의미 검색(임베딩)은 "지난달", "올해 3월" 같은 기간을 이해하지 못한다. 문장이 비슷하면 3년 전 사례와 어제 사례를 구분하지 못하므로, 날짜는 숫자 조건으로 따로 처리해야 한다 |
| 효과 | "지난달 고장난 거", "최근 3개월 프레스 수리" 같은 질문에 정확히 답한다. 최근 사례를 우선 확인하는 현장 습관에도 맞는다 |
| 3종으로 나눈 이유 | 고장 시점, 보고 시점, 작업 시점은 며칠씩 차이가 날 수 있다. 사용자가 말한 "언제"가 무엇인지에 맞춰 필터해야 한다 |
| 목표 | G1, G2 |

#### (4) 본문 5종: 장비개요, 작업명, 고장현상 및 고장원인, 조치내용 및 대책방안, 작업내용

| 구분 | 내용 |
|---|---|
| 무엇을 | 문장형 항목을 합쳐 `full_text`를 만들고 의미 검색(임베딩)에 쓴다 |
| 목적 | 사용자가 증상을 자기 말로 설명해도 비슷한 사례를 찾는다 |
| 근거 | 문제 2, 4. 고장수리내역은 양식이 자유로워서 같은 고장도 "누유", "기름 샘", "오일 새어 나옴"처럼 다르게 적힌다. 키워드로는 못 찾고 의미로 찾아야 한다 |
| 장비개요·작업내용 추가 이유 | 증상과 조치 외에 장비 구조와 작업 과정에도 검색 단서가 많다. 넣을수록 의미 검색이 참고할 문맥이 풍부해진다 |
| 식별자를 본문에서 뺀 이유 | 모델명 같은 값이 본문에 섞이면, 증상은 다른데 모델명만 같은 사례가 의미 점수를 높게 받는다. 식별자는 식별자 검색이, 의미는 의미 검색이 맡도록 역할을 분리한다 |
| 목표 | G1, G2 |

#### (5) 부품 테이블 분리: 사용부품명, 규격, 수량

| 구분 | 내용 |
|---|---|
| 무엇을 | 부품을 `repair_parts` 테이블에 한 줄씩 저장한다 |
| 목적 | 한 사례에 부품이 여러 개여도 빠짐없이 저장하고 검색한다 |
| 근거 | 수리 한 건에 부품 여러 개를 쓰는 경우가 일반적이다. 한 칸에 몰아넣으면 "오링, 패킹, 볼트"처럼 문자열이 섞여서 정확한 검색과 집계가 어렵다 |
| 효과 | "이 부품 쓴 사례" 검색이 정확해진다. 나중에 "부품별 사용 횟수", "재고 예측" 같은 기능으로 확장할 수 있다 |
| 목표 | G2, G3 |

#### (6) 원문(`*_raw`) 보존

| 구분 | 내용 |
|---|---|
| 무엇을 | 날짜와 수량은 정규화한 값과 원문을 둘 다 저장한다 |
| 목적 | 변환이 잘못되어도 원래 값을 확인하고 다시 처리할 수 있다 |
| 근거 | 엑셀 날짜는 형식이 제각각이다(문자열, 일련번호, 점 구분 등). 파싱 실패를 데이터 손실로 만들지 않기 위함이다 |
| 목표 | G1 |

### 9.3 처리 방식별 근거

| # | 설계 | 목적 | 근거 (문제 번호) | 사용자 체감 효과 | 목표 |
|---|---|---|---|---|---|
| 1 | **질의 분석을 맨 앞에** (LLM → JSON) | 질문을 식별자, 날짜, 의미로 나눈 뒤 검색한다 | 1, 2, 6. 정규식은 표현이 조금만 달라도 놓친다. LLM은 문장 구조와 무관하게 항목을 뽑는다 | 긴 질문, 구어체 질문도 잘 알아듣는다 | G2, G3 |
| 2 | **식별자 정규화** (`MC 4` → `MC4`) | 표기 차이로 놓치는 것을 막는다 | 현장 입력은 대소문자, 띄어쓰기, 하이픈이 제각각이다 | 대충 입력해도 찾는다 | G2 |
| 3 | **식별자 검색과 의미 검색 독립 실행** | 한쪽이 실패해도 다른 쪽이 결과를 낸다 | 1. 기존에는 식별자를 못 찾으면 의미 검색까지 막혔다 | 모델명을 몰라도 증상만으로 찾는다 | G2 |
| 3-1 | **2단계 의미 검색 (같은 설비 먼저 → 전체)** | "같은 설비 + 비슷한 증상"을 가장 먼저 보여준다 | 식별자는 맞는데 내용이 다른 경우, 기존 구조는 다른 설비 결과나 증상이 다른 같은 설비 결과만 보여줬다. 같은 설비의 비슷한 증상을 우선으로 올리는 장치가 없었다 | 내 설비의 비슷한 고장 이력을 먼저 보고, 없으면 다른 설비 사례로 보완한다 | G1, G2 |
| 3-2 | **같은 설비라도 임계값을 낮추지 않음** | 식별자만 맞는 사례가 "비슷한 증상"으로 위장해 들어오는 것을 막는다 | 가산점을 주면 증상이 다른 같은 설비 사례가 임계값을 넘을 수 있다 | "비슷한 사례"라고 표시된 것은 실제로 증상이 비슷하다 | G1 |
| 4 | **pg_trgm으로 식별자 유사 일치** | 오타와 부분 일치를 허용한다 | 정확 일치만 쓰면 한 글자 오타에도 실패한다. PostgreSQL 안에서 처리해 별도 시스템이 필요 없다 | 오타가 있어도 찾는다 | G2, G3 |
| 5 | **결과 최대 3개** | 비슷한 사례를 비교하며 참고하게 한다 | 8. 1개만 보여주면 그 1개가 틀렸을 때 대안이 없다 | 여러 조치 방법을 비교해서 고를 수 있다 | G1, G2 |
| 6 | **임계값(THRESHOLD)** | 충분히 비슷한 것만 보여준다 | 유사도 순위 1등이라도 실제로는 관련 없을 수 있다 | 엉뚱한 결과가 줄어든다 | G1 |
| 7 | **후처리 (식별자 2개 이상 일치 목록)** | 의미가 애매해도 같은 설비 이력을 보여준다 | 7. 임계값 미달 시 처리가 없던 문제를 해결한다 (회의 결정 사항) | "결과 없음" 대신 참고할 이력을 받는다 | G2 |
| 8 | **CORE_IDS 조건** | 변별력 낮은 항목만 일치한 결과를 거른다 | 식별자가 8개로 늘면 "보고자 + 작업구분"만 같아도 2개 일치가 된다. 이는 다른 설비일 가능성이 높다 | 관련 없는 설비 이력이 섞이지 않는다 | G1 |
| 9 | **결과 없음(`none`) 명시** | 확신이 없으면 보여주지 않는다 | 고장수리는 틀린 정보를 보여주면 안 된다 (회의 결정 사항) | 챗봇 답을 믿을 수 있다 | G1 |
| 10 | **mode 표시와 안내 문구** | 결과가 어떤 근거로 나왔는지 알려준다 | 같은 목록이라도 "증상이 비슷함"과 "모델만 같음"은 신뢰도가 다르다 | 결과를 얼마나 믿을지 스스로 판단할 수 있다 | G1 |
| 11 | **"매우 유사"(0.9 이상) 강조** | 가장 확실한 사례를 바로 눈에 띄게 한다 | 3개 중 무엇부터 볼지 고민하는 시간을 줄인다 | 가장 확실한 사례부터 바로 본다 | G2 |
| 12 | **생성 없이 검색만 (Retriever only)** | LLM이 내용을 지어낼 여지를 없앤다 | 생성 단계가 있으면 그럴듯하지만 틀린 조치 방법을 만들어낼 수 있다(환각) | 화면의 모든 내용이 실제 기록이다 | G1 |
| 13 | **원본 시트 PDF로 표시** | 기록을 원래 모습 그대로 보여준다 | 엑셀 텍스트는 깨지거나 그림이 빠질 수 있다. 수리 기록은 그림과 표가 중요하다 | 현장에서 보던 양식 그대로 확인한다 | G1 |
| 14 | **`upsert_case()` 하나로 적재** | 새 데이터를 같은 방식으로 계속 추가한다 | 3, 5. 하드코딩 없이 데이터가 늘어나도 그대로 동작한다 | 새로 입력된 수리 기록이 바로 검색된다 | G3 |
| 15 | **설정값 분리 (config.py)** | 코드 수정 없이 기준을 조정한다 | 임계값은 데이터가 늘면 다시 맞춰야 한다. 고객사마다 기준이 다를 수 있다 | (운영) 빠른 조정이 가능하다 | G3 |
| 16 | **평가셋 + 지표** | 감이 아니라 숫자로 성능을 증명한다 | 회의에서 예로 든 0.5 같은 값은 모델과 데이터마다 맞는 값이 다르다 | (팀) 개선 여부를 객관적으로 판단한다 | G1, G3 |

### 9.4 답할 수 있는 질문 비교 (기존 vs 변경)

| 질문 예시 | 유형 | 기존 설계 | 변경 설계 | 가능하게 한 설계 |
|---|---|---|---|---|
| "MC4 누유 수리 사례" | 식별자 + 증상 | ○ | ○ | — |
| "프레스 아래로 기름 새는데 어떻게 고쳐?" | 식별자 없음, 증상만 | ✕ (식별자 미검출) | ○ | 독립 검색, 의미 검색 |
| "2공장 mc 4 프레스가 작업 중에 소리가 나다가 멈췄는데 예전에 비슷한 거 있었나 해서" | 긴 구어체 | △ (키워드 성능 저하) | ○ | 질의 분석 LLM |
| "Mc-4 누유" | 표기 차이 | ✕ | ○ | 정규화, pg_trgm |
| "지난달 고장난 프레스 수리 이력" | 기간 | ✕ | ○ | 날짜 3종, 날짜 필터 |
| "오링 교체한 사례 있어?" | 부품 | ✕ | ○ | 부품 테이블 |
| "긴급수리였던 것만" | 작업 성격 | ✕ | ○ | 작업구분 |
| "MC4 2공장 이상해" | 모호한 증상 | ✕ (결과 없음 처리 없음) | ○ (후처리) | 후처리 로직 |
| "MC4 모터 타는 냄새" (MC4 이력은 누유뿐) | 식별자 일치, 내용 불일치 | ✕ (MC4 누유 사례를 그대로 보여줄 위험) | ○ (다른 설비 비슷한 증상 + 안내) | 2단계 의미 검색 |
| "컨베이어 벨트 느려요" (데이터 없음) | 정답 없음 | ✕ (가장 비슷한 1개를 그대로 보여줄 위험) | ○ (찾지 못함 안내) | 임계값, `none` |

○ 가능 · △ 부분 가능 · ✕ 불가 / 위험

> 위 표는 설계상 기대 동작이다. 실제 수치는 6.2절 평가에서 유형별 Recall@3으로 확인한다.

### 9.5 감수하는 비용과 대응

더 좋은 챗봇이 되는 대신 늘어나는 부담도 있다. 이를 숨기지 않고 대응 방안과 함께 정리한다.

| 비용 / 위험 | 내용 | 대응 |
|---|---|---|
| 응답 시간 증가 | 질의 분석에 LLM(GITC)을 한 번 더 호출한다 | 질의 분석은 작은 모델로도 충분하다. 타임아웃 3초, 평균 2초 이내를 기준으로 측정한다 |
| LLM 장애 | GITC API가 응답하지 않을 수 있다 | 실패 시 의미 검색만으로 진행해 검색은 멈추지 않는다 (4.8절) |
| LLM 비용 | 질의마다 호출 비용이 발생한다 | 출력이 짧은 JSON이라 호출당 비용이 작다. 같은 질의는 캐싱한다 |
| 추출 오류 | 항목이 17개로 늘어 잘못 추출될 가능성도 늘어난다 | 6.1 리포트로 항목별 null 비율과 라벨 위치를 확인하고, 원문(`*_raw`)을 보존한다 |
| 구현량 증가 | 테이블 2개, 날짜·부품 처리가 추가된다 | 7장 순서대로 단계별로 검증하며 진행한다 |
| 개인정보 | 보고자 이름을 검색에 쓰는 것 | 사용 여부를 확인받는다 (미결 #9). 쓰지 않더라도 저장은 해 둔다 |

## 10. 준비 현황 (설계 기준)

### 10.1 설계가 완료된 것

1. **설계 변경 방향 확정:** 기존 키워드 4개 방식의 문제 9가지와 변경 방향 정리 (1장)
2. **원본 처리 방침:** 원본은 엑셀, 검색은 엑셀에서 추출한 텍스트, 표시는 시트별 PDF (3.1절)
3. **추출 항목 17개:** 양식 전체 항목을 식별자, 날짜, 본문, 부품 용도로 분류 (3.2절)
4. **정규화 규칙:** 식별자(대소문자·공백), 날짜, 수량 변환 규칙과 원문 보존 (3.3절)
5. **DB 구조:** `repair_cases` + `repair_parts` 테이블과 인덱스 SQL (3.4절)
6. **질의 분석:** 출력 JSON(식별자 8개 + 날짜 필터 + 의미 질의), 시스템 프롬프트, 실패 처리 (4.1절)
7. **LLM 연결:** GITC API를 1순위로, `llm_client.py`로 교체 가능하게 구성하고 적합성 기준 마련 (4.8절)
8. **식별자 검색:** 필드별 일치 판정 방식과 SQL (4.2절)
9. **2단계 의미 검색:** 같은 설비 먼저 → 전체로 채움. "식별자는 맞는데 내용이 다른 경우" 해결 (4.3절, 4.4절)
10. **판단·후처리 규칙:** semantic → identifier_fallback → none, CORE_IDS 조건, 안내 문구 (4.4절)
11. **설정값:** 임계값, 강조 기준, 결과 개수 등을 config로 분리 (4.5절)
12. **API와 화면:** 검색·PDF API, 같은 설비/다른 설비로 나눈 카드 표시 (4.6절, 4.7절)
13. **검증 계획:** 엑셀 깨짐·양식 검증, 평가셋 유형, 지표, 임계값 선택 기준 (6장)
14. **구현 순서:** 9단계와 단계별 산출물 (7장)
15. **설계 근거:** 목표 3가지(G1~G3), 항목별·처리 방식별 근거, 기존 대비 비교표, 비용과 대응 (9장)

### 10.2 구현하면서 확인·확정할 것

1. 엑셀 텍스트 깨짐 여부와 양식 라벨 위치 → 구현 1단계 리포트
2. 양식에 두 번 나오는 "모델명"의 의미 → 샘플 시트 확인
3. GITC API 적합성 (JSON, 정확도, 속도, 데이터 정책) → 구현 5단계 테스트
4. 임계값(THRESHOLD) 최종값 → 구현 9단계 평가
