# 삼광 설비 챗봇 — 고장수리내역 검색 방식 비교

> **GUIDE_13 — 고장수리내역·작업지시서 검색·표시 설계 문서.**

1. **범위**: 고장수리내역·작업지시서(엑셀) 검색·표시 방식. 매뉴얼은 다루지 않는다.
2. **기준(2026-10-14 갱신)**: **고장수리내역은 `docs/고장수리내역_검색_설계서.md`가, 작업지시서는 `docs/작업지시서_ClaudeCode_프롬프트.md`(실행 프롬프트 스크립트 — 원본 설계서 `작업지시서_검색_설계서.md` 자체는 아직 `docs/`에 없음)가 각각 기준 문서다.** **13번은 그 요약·GUIDE_9와의 연결용**으로 다시 정리한다 — 세부 SQL·코드·표는 원본 파일을 본다.
3. **현재 결론**: 0~6절은 "여기까지 어떤 안들을 거쳤는지"의 과정 기록(전부 폐기, 요약만 남김). **7절부터가 고장수리내역의 최종 설계**, **12절부터가 작업지시서의 최종 설계**다. **순서(2026-10-14 재정렬)**: 고장수리내역 내용(0~11절)을 먼저 전부 끝내고, 작업지시서(12~13절)를 맨 뒤로 옮겼다 — 전에는 작업지시서가 고장수리내역 과정기록(0~6절)과 최종설계(옛 9~13절) 사이에 끼어 있어 읽을 때 헷갈린다는 지적을 반영. 작업지시서(12·13절)는 그 뒤 `작업지시서_ClaudeCode_프롬프트.md`가 추가되면서 기존 5단계 설계(시트 단위)를 단계·섹션 단위 설계로 다시 교체했다.
4. **전제**: 아직 아무것도 구현·테스트하지 않았다. 원본 설계서 자체도 "설계 확정 대기(목요일 오후 미팅 검토 예정)" 상태다.

## 0~2. 고장수리내역 — 1차 폐기된 안 (방식 A·B)

- **방식 A(벡터 단독, 폐기)**: `text`(장비명+이상부위+고장현상) 임베딩만으로 유사도 검색. 코드·정확 일치에 약해서 B로 교체.
- **방식 B(하이브리드, 폐기)**: 식별자 필드(처음 `equipment` 1개 → `장비명`·`모델명`·`규격/사양`·`현장명` 4개로 확장)를 정확 매칭으로 먼저 거르고 그 안에서 벡터 유사도로 재순위. 실측으로 "식별자 필드를 미리 고정하는 것 자체가 불안정하다"는 게 드러나서 폐기.

## 3. 방식 C — 원본 그대로 보여주기 (개념은 유지, 형식은 PDF로 확정)

**어떻게 보여주나**: 검색 결과의 근거를 파싱된 필드값이 아니라 **원본 시트 그대로** 보여준다. 파싱 오류 가능성이 0이라 정확도가 생명인 고장수리내역·작업지시서 둘 다에 안전한 표시 방식.

**갱신(2026-10-14)**: PDF와 엑셀 뷰어 중 뭘 쓸지 저울질했었는데(8절에서 다뤘던 내용), `고장수리내역_검색_설계서.md`는 **PDF 변환(LibreOffice headless, 시트 1장=PDF 1개)으로 확정**해서 적었다. 다만 설계서 자체도 "결과 표시 방식(PDF 변환 vs 엑셀 뷰어) 최종 확정 — 허이사님 확인 필요"로 남겨뒀다(설계서 8장 #3) — **확정이 아니라 1순위 제안**으로 이해한다.

## 4~6. 고장수리내역 — 2차 폐기된 안 (이 세션의 순수 의미 기반 검색)

이번 세션에서 "필드 지정을 버리고 전체 의미 기반 검색으로"(옛 9~12절, 10/14 오전~낮 작업) 설계했었다. 방향 자체(필드 하나로 안 고정한다, 의미 검색을 쓴다)는 맞았지만, `고장수리내역_검색_설계서.md`가 **같은 문제의식을 훨씬 정교하게 설계**했다 — 질의 분석(LLM), 식별자 8개, 같은설비/다른설비 구분, 전용 테이블, 생성 없는 검색 전용 구조 등. 그래서 이 세션의 옛 9~12절 내용은 **전면 교체**하고, 아래 7절부터 새 설계로 다시 쓴다.

## 7. 고장수리내역 최종 설계 — `고장수리내역_검색_설계서.md` 기준 (2026-10-14)

**핵심 목표 3가지(G1·G2·G3)** — 모든 설계 결정은 이 세 가지 중 하나 이상을 위한 것이다.

| 목표 | 의미 |
|---|---|
| **G1. 틀린 결과를 보여주지 않는다** | 확신이 없으면 안 보여주거나, 왜 보여주는지 밝힌다 — 현장 작업자가 실제 수리에 참고하므로 틀리면 사고·설비 손상으로 이어질 수 있음 |

**전체 처리 흐름**

```
[오프라인: 적재]
엑셀 → 시트 분리 → 양식 항목 17개 추출 → 정규화(식별자)/날짜 파싱
               └→ 시트별 PDF 변환
                                 → 본문 임베딩(bge-m3) → PostgreSQL(repair_cases, repair_parts)

[온라인: 검색]
사용자 질의
  → ① 질의 분석(LLM=GITC) → {식별자 JSON, 날짜 조건, 의미 질의}
      ├→ ② 식별자 검색(pg_trgm, 날짜 필터) → 같은 설비 후보 집합 S
      └→ ③ 의미 검색(pgvector, 날짜 필터) — 2단계
            1차: S 안에서만 → 임계값 이상 → [같은 설비] 그룹
            2차: 3개가 안 차면 전체에서(1차 결과 제외) → 임계값 이상 → [다른 설비] 그룹으로 채움
  → ④ 판단: (1·2차 있음→최대3개, 같은설비 우선) / (없음+식별자2개↑→폴백 목록) / (둘다없음→빈목록+메시지)
  → ⑤ 카드 목록 표시 → 클릭 → 원본 시트 PDF
```

**이 세션의 옛 9~12절(폐기) 대비 핵심적으로 달라진 것**

| 이 세션에서 설계했던 것 | 새 설계(`고장수리내역_검색_설계서.md`) |
|---|---|
| 질의를 전처리 없이 그대로 임베딩 | **LLM(GITC)이 질의를 먼저 분석**해서 식별자·날짜·의미질의 3갈래로 분리 |
| 식별자 4개(장비명·모델명·규격사양·현장명) | 식별자 **8개**(+보고자·작업명·작업구분·사용부품명) |

| `manual_chunks` 재사용(`doc_type='repair_log'`) | **전용 테이블** `repair_cases` + `repair_parts` 신설 |
| 날짜는 "별도 필터"라고만 언급, 세부 설계 없음 | 날짜 3종(보고일자·고장발생일·작업일시) 정규화 + LLM이 "지난달" 같은 표현을 기간으로 변환 |
| GITC로 답변까지 생성(Generation, 구 12절) | **생성 없음 — 검색 결과만 카드로 표시**(Retriever만 사용, 환각 위험을 구조적으로 차단) |
| 식별자는 글자 포함 여부만(정확 일치) | `pg_trgm`으로 **오타 허용 유사 일치** |
| 임계값만으로 "같은 설비/다른 설비" 구분 없이 섞임 | 식별자는 맞는데 증상이 다른 경우 vs 설비는 다른데 증상이 비슷한 경우를 **분리해서 라벨링** |

**DB 스키마 핵심**

```sql
CREATE TABLE repair_cases (
  case_id TEXT PRIMARY KEY, source_file TEXT, sheet_name TEXT, pdf_path TEXT,
  report_date DATE, failure_date DATE, work_datetime TIMESTAMP,          -- 날짜 3종(+*_raw 원문 보존)
  reporter TEXT, equipment TEXT, model TEXT, spec TEXT,
  work_name TEXT, site TEXT, work_type TEXT,                             -- 식별자 원본
  reporter_n TEXT, equipment_n TEXT, model_n TEXT, spec_n TEXT,
  work_name_n TEXT, site_n TEXT, work_type_n TEXT,                       -- 식별자 정규화본
  equipment_overview TEXT, symptom_cause TEXT, action_plan TEXT, work_detail TEXT,
  full_text TEXT, embedding VECTOR(1024)                                 -- 의미 검색용
);
CREATE TABLE repair_parts (                                              -- 부품은 한 사례에 여러 줄 가능해서 별도 테이블
  id BIGSERIAL PRIMARY KEY, case_id TEXT REFERENCES repair_cases(case_id) ON DELETE CASCADE,
  part_name TEXT, part_name_n TEXT, part_spec TEXT, part_qty NUMERIC, part_qty_raw TEXT
);
-- 의미 검색: HNSW(embedding), 식별자 검색: GIN+pg_trgm(각 *_n 컬럼), 날짜: 일반 인덱스
```

**양식 17개 항목 분류**(식별자 8 / 날짜 3 / 본문 5 / 부품 3) — 9번·13번 이전 버전이 4~5개로 추리던 것과 달리, **엑셀 양식 전체 항목을 다 추출**해서 용도별로 나눈다. 식별자를 본문(`full_text`)에서 분리하는 이유: 모델명 같은 값이 본문에 섞이면 "증상은 다른데 모델명만 같은" 사례가 의미 점수를 잘못 높게 받기 때문 — 식별자와 의미를 독립적으로 검색하기 위함. 세부 컬럼 목록·정규화 규칙(`norm()` 함수: NFKC+공백/하이픈 제거+대문자화)·SQL 전체는 원본 설계서 3장을 본다.

**모듈 구성**: `ingest/`(시트분리·정규화·임베딩적재), `search/`(질의분석·검색·판단·설정), `api/`(라우트), `scripts/`(엑셀검증·평가). 원본 설계서 2.2절에 전체 트리.

## 8. 질의 분석 · 검색 · 판단 로직

**① 질의 분석(LLM=GITC, `search/query_parser.py`)**: 질문을 받아 아래 JSON으로 분해한다. temperature 0, few-shot 3~4개. 실패(JSON 깨짐) 시 1회 재시도 → 그래도 실패하면 식별자·날짜는 null, `semantic_query`=원문으로 폴백(검색 자체는 멈추지 않음).

```json
{"identifiers": {"reporter": null, "equipment": "프레스", "model": "MC4", "spec": null,
                  "work_name": null, "site": "2공장", "work_type": null, "part_name": "패킹"},
 "date_filter": {"field": "failure_date", "from": "2026-09-01", "to": "2026-09-30"},
 "semantic_query": "프레스 하부 기름 누유 패킹 교체"}
```

**② 식별자 검색(`pg_trgm`)**: null 아닌 식별자만 조건으로. 장비명·모델명·규격/사양·작업명·현장명은 정확 일치 또는 `similarity ≥ 0.6`(TRGM_MIN), 작업구분·보고자는 정확 일치만, 사용부품명은 `repair_parts`에서 유사 일치. `match_count`(몇 개 일치했는지) 내림차순 정렬 → **같은 설비 후보 집합 S**를 만든다.

**③ 의미 검색(pgvector, 2단계)**: 질의 임베딩과 `1 - (embedding <=> qv)`로 코사인 유사도 계산.
- **1차**: `include_ids=S`(같은 설비 안에서만) → `score ≥ THRESHOLD`
- **2차**: 1차가 3건 미만이면 `exclude_ids=1차결과`로 전체에서 채움 → `score ≥ THRESHOLD`
- **S가 비어있으면(식별자 추출 자체가 안 됐으면) 1차를 건너뛰고 2차(전체)만 수행** — 즉 식별자가 하나도 없어도 의미 검색은 항상 돈다

**④ 판단**(`search/pipeline.py`)

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 같은 설비(S) 안에서 `score ≥ THRESHOLD` | 우선 표시(`same_equipment`) |
| 2 | 1이 3개 미만이면 전체에서 `score ≥ THRESHOLD`(1 제외) | 남은 자리 채움(`other_equipment`) |
| 3 | 1·2 모두 없고 `match_count ≥ 2`(핵심 식별자 1개 이상 포함) | 일치 개수 순 최대 3개(`identifier_fallback`) |
| 4 | 전부 없음 | 빈 목록 + "유사한 수리 사례를 찾지 못했습니다"(`none`) |

**핵심 원칙**: 같은 설비(S)라고 임계값을 낮추거나 가산점을 주지 않는다 — **의미 점수는 1차·2차 똑같은 기준**을 쓴다. 안 그러면 "식별자만 맞고 증상은 다른" 사례가 "비슷한 증상"인 것처럼 섞여 들어온다(G1). 식별자만 맞는 사례는 3번(후처리)에서만, "정확히 일치하는 사례는 없지만 참고용"이라는 안내문과 함께 보여준다.

**"유사도는 낮지만 사실은 맞는 사례"는 어떻게 되나 (G1 vs G2 긴장 지점)**: 질의 문장과 실제 사례의 표현이 많이 달라서 코사인 유사도가 `THRESHOLD`를 못 넘는 경우, 두 경로로 갈린다.
- **식별자가 하나라도 살아있으면(① 질의 분석에서 장비명·모델명·현장명 등이 뽑혔으면)**: 1·2차 의미검색이 0건이어도 **판단 3번(`identifier_fallback`)이 구제**한다. 식별자 `match_count ≥ 2`면 의미 점수와 무관하게 상위 3건을 "정확히 일치하는 사례는 없지만, 같은 장비·모델·현장의 수리 이력입니다"로 보여준다 — 놓치지 않는다.
- **식별자도 거의 안 뽑히고 의미 점수도 낮으면(예: "기름 새는 거 전에 고친 적 있나"처럼 장비 정보 없이 표현도 사례와 많이 다른 질문)**: 지금 구조상 **진짜로 놓칠 수 있다** — `none`으로 끝남. 이게 G1(틀린 걸 보여주지 않는다)과 G2(어떻게 물어봐도 찾는다)가 정면충돌하는 지점이다. `THRESHOLD`를 낮추면 G2는 좋아지지만 G1(엉뚱한 사례 노출)이 나빠진다.
- **대응**: 설계로 100% 막을 수 있는 문제가 아니라서, 10절 평가 계획으로 **측정해서** 다룬다 — THRESHOLD를 0.30~0.80 전 구간으로 돌려보면서 오답 노출률이 거의 0인 범위 안에서 Recall@3이 최고인 지점을 찾는다(느낌이 아니라 실측으로 확정). 11절 미결사항 #10("긴 질의의 의미 검색 성능 한계")과 같은 문제다.

**`CORE_IDS` 조건**: 식별자가 8개로 늘면서 "보고자+작업구분"처럼 변별력 낮은 항목만 같아도 2개 일치가 될 수 있다. 그래서 S·폴백 둘 다 `equipment·model·site·part_name`(핵심 식별자) 중 **최소 1개는 포함**해야 인정한다.

| 이름 | 초기값 | 설명 |
|---|---|---|
| THRESHOLD | 0.6(잠정) | 평가로 확정(10절) |
| HIGHLIGHT | 0.9 | "매우 유사" 강조 기준 |
| TOP_N | 3 | 화면 표시 최대 건수 |
| MIN_ID_MATCH | 2 | 폴백 발동 최소 일치 수 |
| CORE_IDS | equipment, model, site, part_name | 폴백·S 판정의 필수 포함 조건 |
| TRGM_MIN | 0.6 | 식별자 유사 일치 기준 |

**화면 — 생성형 답변 없음, 카드만**: `group`(같은설비/다른설비)별로 나눠 표시. `identifier_fallback`은 "정확히 일치하는 사례는 없지만, 같은 장비·모델·현장의 수리 이력입니다", `none`은 "유사한 수리 사례를 찾지 못했습니다". `highlight`(score≥0.9)는 "매우 유사" 배지. 카드 클릭 → 원본 PDF.

## 9. 동작 예시 (설계서 5장 그대로)

| 경우 | 질의 | 처리 | 결과 |
|---|---|---|---|
| A | "2공장 mc 4 프레스 기름 새는데 예전에 어떻게 고쳤어?" | 1차(같은설비) 0.83/0.76 → 2차로 0.71 채움 | 같은설비 2 + 다른설비 1 |
| A-2 | "MC4 2공장 모터에서 타는 냄새 나요"(MC4 이력은 누유뿐) | 1차 전부 임계값 미달 → 2차에서 MC6 모터과열 0.78 | 다른설비 1건 + "MC4의 수리 이력은 있지만 비슷한 증상은 없습니다" |
| B | "MC4 2공장 이상해" | 의미 최고점 0.42(미달) → 모델명·현장명 2개 일치 | `identifier_fallback` |
| C | "컨베이어 벨트 속도가 느려요"(데이터 없음) | 의미·식별자 모두 미달 | `none` |
| D | "지난달 패킹 교체한 작업 뭐 있었어?" | 날짜필터(지난달)+부품"패킹"+의미검색 | 기간 내 사례만 |

**답할 수 있게 된 질문 유형(요약)**: 식별자 없는 증상만 질문, 긴 구어체, 표기 오타(`Mc-4`), 기간 질문, 부품 질문, 작업구분 질문, 모호한 증상(후처리로 커버), 데이터 없는 질문(`none`으로 안전 처리) — 전부 기존 4필드 하드매칭 설계에서는 ✕였던 것들. 전체 비교표는 설계서 9.4절.

## 10. 검증 계획과 완료 기준

- **엑셀 검증**(`scripts/check_excel_text.py`): 병합셀·빈셀 비율·특수공백·이미지 위치, 양식 17개 라벨 위치가 시트마다 같은지 리포트 — "텍스트 대신 PDF로 보여준다" 결정의 근거.
- **검색 평가**(`scripts/eval.py`): 평가 질의 약 30개(`short/long/no_identifier/typo/date/part/no_answer` 유형). `THRESHOLD`를 0.30~0.80까지 0.05 단위로 바꿔가며 **Recall@3**·**오답 노출률**·`mode` 비율 측정. **선택 기준: 오답 노출률이 0에 가까운 범위에서 Recall@3 최고점.** bge-m3는 무관한 문장끼리도 코사인 점수가 높게 나올 수 있어 "0.5"를 그냥 쓰지 않고 반드시 측정해서 정한다.
- **완료 기준**: 시트 수=레코드 수=PDF 수 / 항목 17개 null 비율 리포트 / `embedding` NULL 0건 / 날짜 파싱 실패 건수 확인 / `search_repair()`가 3개 mode 전부 반환(단위테스트) / 카드 표시·PDF 열림 확인 / 평가로 THRESHOLD 확정.

## 12. 작업지시서 최종 설계 — `작업지시서_검색_설계서.md` 기준 (2026-10-14 갱신)

**갱신 경위**: 기존 5단계(식별자 풀+정확매칭+벡터재순위+복수후보+사람확인) 설계는 "시트 1장=1건"이라는 전제로 짜여 있었다. 그런데 `docs/작업지시서_ClaudeCode_프롬프트.md`(실행용 프롬프트 스크립트)를 보니, 작업지시서는 고장수리내역과 달리 **시트 한 장 안에 여러 "단계(step)"가 순서대로 있는 절차서**라는 게 전제다 — 그래서 기존 설계처럼 시트 전체를 하나의 매칭 단위로 보면 안 되고, 단계·섹션 단위로 더 잘게 다뤄야 한다. 이 절을 그 구조로 다시 쓴다.

> **주의(2026-10-14)**: 원본 설계서 `docs/작업지시서_검색_설계서.md` 자체는 아직 `docs/`에 없고, 그걸 실행하는 **프롬프트 스크립트만** 있다. 아래는 그 스크립트에서 읽어낼 수 있는 구조를 정리한 것 — 세부 JSON 스키마·SQL 전문·intent 8종 전체 목록·식별자 우선순위표 같은 디테일은 원본 설계서가 와야 채울 수 있다(표에 "원본 참고"로 표시).

**기존 5단계 설계 대비 핵심적으로 달라진 것**

| 기존 설계(시트 단위) | 새 설계(단계·섹션 단위) |
|---|---|
| 식별자 5개(표준번호·품번·모델명·공정명·부품명) | 식별자 **6개**(+작업명) |
| 매칭 단위 = 시트 전체 1건 | 문서(시트)→**단계(step)**→**섹션(section)** 3단계 구조 |
| 결과 = 후보 여러 건을 사람이 눈으로 비교 | **앵커(anchor) 찾기** — "지금 몇 단계 얘기냐"를 점수로 판단해 바로 그 단계로 이동 |
| 대화 맥락 없음(질문마다 처음부터 다시 찾음) | **세션 맥락** — "그다음은?"하면 직전 단계 이어서 이동(`CONTEXT_TTL`) |
| 판단 = 일치/불일치 2갈래 | 판단 **5갈래**: high(바로 이동)/low(확인 질문)/doc_only/ambiguous(문서 선택)/none |
| 고장수리내역과 코드 공유 없음 | `common/`(정규화·LLM클라이언트·PDF변환)을 고장수리내역과 **공유** |

**데이터 구조(3단계)**: 문서(`ws_documents` — 표준번호·품번·모델명·공정명·부품명·작업명 등 식별자) → 단계(`ws_steps` — `step_no`·`step_title`·캡션·작업내용·소요값·공구·부품, 번호가 1부터 빠짐없이 이어짐) → 섹션 청크(`ws_chunks` — 단계를 다시 섹션별로 쪼갠 것, 텍스트 앞에 `[{작업명}] {step_no}단계 {step_title} - ` 맥락을 붙여서 임베딩). **DB**: `work_standards`+`work_steps`+`work_chunks`+`work_parts` 4개 테이블(고장수리내역의 `repair_cases`+`repair_parts`와 같은 급의 전용 테이블).

**여기서 "청킹"을 실제로 쓴다** — 고장수리내역은 "시트 1장=레코드 1건"이라 청킹이 필요 없다고 했지만, 작업지시서는 한 시트 안에 여러 단계·섹션이 있어서 **섹션 단위 청킹이 진짜 필요**하다. 다만 평가 단계(아래 6.2절 항목)에서 "섹션별 벡터 vs 단계 전체를 벡터 1개로"를 실제로 비교해서, 더 잘 맞는 쪽으로 확정할 계획 — 청킹 단위조차 아직 확정이 아니라 측정 대상이다.

**공통 모듈 공유**: `common/normalize.py`(식별자 정규화, 고장수리내역의 `norm()`과 동일 규칙), `common/llm_client.py`(`LLMClient`/`GITCClient`, 고장수리내역 8절 §8.1과 동일 클래스 재사용), `common/pdf_convert.py`(시트→PDF, LibreOffice headless). 고장수리내역 코드에서 뽑아내 공용화하는 작업이라, **고장수리내역 테스트가 분리 전후로 똑같이 통과하는지 먼저 확인**하고 진행한다.

**검색 흐름**

```
질문 → ① 질의 분석(parse_ws_query, GITCClient)
         → {identifiers(6개), intent(8종 중 하나), step_ref, semantic_query, raw_query}
      → ② 식별자 검색(ws_identifier_search) — WS_CORE_IDS 1개 이상 일치(pg_trgm) → 후보 문서 집합 D
      → ③ 앵커 찾기(find_anchor)
            검색 문장 = step_ref 있으면 step_ref, 없으면 semantic_query
            intent별 우선 섹션 다르게 적용(공구 질문→공구 섹션 우선 등, config)
            1차: D 안에서 → 2차: 전체(1차 미달 시)
            같은 단계 안 여러 섹션이 걸리면 단계 단위로 묶어 최고 점수 사용
      → ④ 판단(search_work_standard, 5갈래)
            high        → 바로 그 단계로 이동
            low         → "이 단계를 말씀하신 건가요?" 확인 질문 + 추정 단계 같이 표시
            doc_only    → 단계는 특정 안 되고 문서(작업지시서)만 특정된 경우
            ambiguous   → 서로 다른 문서의 앵커 점수 차이가 AMBIGUITY_GAP 이내 → 문서 선택지 제시
            none        → 못 찾음
      → ⑤ 화면: 단계 카드(작업명·모델/공정, 현재/전체 단계, 섹션 원문 그대로, [이전][다음][원본 PDF])
```

**대화 맥락(세션)**: `step_ref`도 식별자도 없는데 `intent`가 `next_step`/`prev_step`/`tools`/`parts`/`spec` 중 하나면, 세션에 저장된 **마지막 `doc_id`·`step_no`**를 앵커로 그대로 쓴다(`CONTEXT_TTL` 지나면 만료) — "그다음은?", "공구는 뭐 필요해?" 같은 후속 질문이 가능해지는 부분. 고장수리내역 쪽엔 이런 세션 개념 자체가 없다(매번 독립 질문) — 작업지시서만의 특징.

**식별자 6개**: 표준번호·품번·모델명·공정명·부품명·**작업명**(기존 5개 설계엔 없던 항목, 실제 체크 스크립트 기준으로 추가됨).

**설정값(`search/work_standard/config.py`, 전부 잠정)**: `WS_THRESHOLD`(평가로 0.40~0.80 사이 확정), `WS_LOW`(0.30~0.60 사이, "확인 질문" 발동 기준), `AMBIGUITY_GAP`(문서 간 점수차 이 이내면 모호 처리), `CONTEXT_TTL`(세션 맥락 유지 시간), `WS_CORE_IDS`(핵심 식별자 구성 — 원본 설계서 4.2절 참고, 현재는 "1개 이상 일치"만 확인됨).

**생성 없음 원칙 동일 적용**: 고장수리내역과 마찬가지로 **LLM이 섹션 내용을 요약·수정하지 않는다** — 원문 그대로 보여준다(Retriever only). 화면에서 confidence가 낮으면(low) 안내 문구, 모호하면(ambiguous) 문서 선택 버튼을 보여줄 뿐, 답을 지어내지 않는다.

**실행 전 반드시 확인할 조건(설계서 7장 0번)**: **허정희 이사님 확인이 끝나기 전에는 구현 순서(13절) 중 프롬프트 1~2까지만 진행**한다 — 단계 분리 규칙이 실제 양식과 맞는지(프롬프트 1 결과) 이사님 확인을 받은 뒤에야 적재·검색 로직(프롬프트 3 이후)으로 넘어간다. 그리고 **작업지시서 저장·전송용 DB는 아직 만들지 않는다**(설계서 8장 #3, 미결 — 검색·조회 기능과는 별개로 보류).

## 13. 구현 순서 — 작업지시서 (Claude Code 프롬프트 0~9)

`작업지시서_ClaudeCode_프롬프트.md`에 있는 실행 순서를 요약한다. 한 번에 한 단계씩, 결과를 확인(특히 1번은 **이사님 확인**)하고 다음으로 넘어가는 방식.

| # | 단계 | 산출물 | 넘어가기 전 확인 |
|---|---|---|---|
| 0 | 현황 파악 | 기존 코드 vs 설계서 모듈 비교표("있음/일부있음/없음") | 현황표가 실제 코드와 맞는지 |
| 1 | 양식·단계 구조 검증 | `scripts/check_ws_structure.py` → `reports/ws_structure.md`(식별자 위치, 단계 구분 방식, 섹션 라벨, 분기 여부, 병합셀·이미지) | **이사님 확인** — 이 확인 전엔 2번까지만 진행 |
| 2 | 공통 모듈 분리 | `common/normalize.py`·`llm_client.py`·`pdf_convert.py` (고장수리내역 코드에서 추출) | 고장수리내역 테스트가 분리 전후 동일하게 통과하는지 |
| 3 | 적재: 문서·단계·섹션 분리 | `ws_documents.jsonl`·`ws_steps.jsonl`·`ws_chunks.jsonl`·`pdf/ws/{doc_id}.pdf` | 시트 1개 결과가 원본과 맞는지(먼저 1개로 검증 후 전체 적용) |
| 4 | DB 스키마+임베딩 적재 | `work_standards/work_steps/work_chunks/work_parts` 테이블, `embed_load.py`(bge-m3) | `step_no`가 빠짐없이 이어지는지, `embedding` NULL 0건 |
| 5 | 질의 분석 | `search/work_standard/query_parser.py` — `parse_ws_query()` | intent 8종 분류 정확도, 응답 시간 |
| 6 | 식별자 검색+앵커 찾기 | `retriever.py` — `ws_identifier_search()`, `find_anchor()` | 표현을 바꾼 질의에서도 앵커를 맞게 찾는지 |
| 7 | 의도별 처리+판단+대화맥락 | `intent_handler.py`, `pipeline.py` — `search_work_standard()` | 예시 A~F·대화 맥락·ambiguous 케이스 통과 |
| 8 | API+화면 | API 4개, 단계 카드 UI(이전/다음/원본보기) | 화면에서 이전/다음/PDF 동작 확인 |
| 9 | 평가+임계값 확정+청킹 비교 | `eval_ws.py` → `reports/ws_eval.md`(의도분류정확도·앵커정확도·최종정답률·**잘못된 다음단계 노출률**·확인질문비율, 임계값 스윕, 섹션별 vs 단계별 청킹 비교) | "잘못된 다음 단계 노출률 0" 조건에서 최적 설정 확인 |

**작업 원칙(프롬프트 0에 명시)**: 설계서에 없는 기능은 추가하지 않는다 / 미검증·가정으로 표시된 부분은 하드코딩하지 말고 config나 분리 함수로 둔다 / 양식 정보가 불확실하면 추측하지 말고 사람에게 물어본다 / 값은 LLM이 바꾸거나 요약하지 않고 원문 그대로(Retriever only) — 모두 고장수리내역의 G1(틀린 거 보여주지 않는다) 원칙과 같은 방향이다.
