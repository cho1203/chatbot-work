# 삼광 설비 챗봇 — GUIDE_8·9·10·12·13 절별 세부 분석

이 문서는 DEVELOPER_GUIDE_8.md·9.md·10.md·12.md·13.md를 각 문서 안에 이미 있는 절 번호 순서 그대로 따라가며 절마다 세부 분석한 결과만 담은 문서다. 원본 5개 문서는 전혀 수정하지 않았고(읽기만 함), 새로 설계를 제안하지도 않았다 — 요약·핵심 수치 확인·확정/제안 구분·상호참조 대조·수치 일치 여부·발견한 점만 기록한다.

## GUIDE_8 분석

GUIDE_8은 "삼광 설비 챗봇 — 다이어그램 모음"(작성일 2026-10-12)이며, 문서 서두에서 스스로 1·2번은 GUIDE_5·GUIDE_6의 확정된 그림을 그대로 옮긴 것, 3번은 GUIDE_7의 글을 그림으로 옮긴 **초안**, 4번은 기존 설계 재사용만으로 구현 가능한 **1차 데모 범위**라고 명시하고 있다. 이 상태 선언을 각 절 분석의 기본 전제로 삼았다.

### 1. 기존 아키텍처 (GUIDE_5)

- **요약**: GUIDE_5의 핵심 아키텍처 다이어그램(계층 구조·PDF/엑셀 색인 순서·질의 실행 순서) 4개를 그대로 옮겨온 상위 절. 이 절 자체는 그림이 없고 1.1~1.4의 묶음 제목 역할만 한다.
- **확정/제안 구분**: 문서 서두 선언대로 **확정**(GUIDE_5 원본 그림 이전).
- **발견한 점**: 괄호 안의 "(0.2절)"·"(0.5절)" 등은 GUIDE_5 쪽 절 번호인데, GUIDE_5는 분석 대상 5개 문서에 포함되지 않아 이번 분석에서 직접 대조는 불가능하다(참고만).

### 1.1 구현을 구성하는 계층 구조 (0.2절)

- **요약**: `index.html → FastAPI → 질의 라우팅 → PostgreSQL pgvector(manual_chunks) / GITC` 로 이어지는 전체 계층과, PDF 2종·엑셀 3종이 각각 임베딩을 거쳐 `manual_chunks`로 들어가는 입력 경로를 보여주는 flowchart.
- **핵심 이름**: `manual_chunks`, `GITC`, `page_align`, `bge-m3`.
- **상호참조 검증**: 같은 그림이 GUIDE_9 0.1절에도 (탭 3개 대응 구조로 확장된 버전으로) 다시 나온다. 뼈대(`U→A→R→V/G`, `PDF→PDFE→V`, `EXCEL→EXCE→V`)는 완전히 동일해서 두 문서 간 계층 구조 자체는 어긋나지 않는다.
- **발견한 점**: 이 절의 그림은 "엑셀 3종"이라고만 되어 있어 작업지시서/고장수리내역 구분이 없다. GUIDE_9 0.1절 그림은 이를 ①매뉴얼·②작업지시서·③고장수리내역 3갈래로 명시적으로 쪼갰다 — 오류는 아니고 GUIDE_9가 더 세분화된 후속판이라는 관계다.

### 1.2 색인 준비 순서 — PDF (0.5절)

- **요약**: `rebuild_originals.py`가 원본 PDF 2권을 받아 조각·110dpi 페이지 이미지로 만들고, `index_to_pgvector.py`가 조각이 바뀐 뒤에만 bge-m3 임베딩 후 `manual_chunks`를 전체 교체 적재하는 시퀀스.
- **핵심 이름**: `rebuild_originals.py`, `merged_ko.json`/`merged_en.json`, `index_to_pgvector.py`, 110dpi.
- **상호참조 검증**: GUIDE_9 0.3절의 같은 제목 시퀀스와 비교하면 참가자·메시지 흐름이 동일하고, GUIDE_9 쪽에 "텍스트 정규화(아래) 적용 후 청킹" 한 줄이 더 들어간 것만 차이다. GUIDE_12 1절의 `rebuild_originals.py` 함수 분해(`normalize_text`, `hangul_ratio` 등)와도 역할이 맞아떨어진다.
- **확정/제안 구분**: 확정(GUIDE_5 원본 그림).

### 1.3 색인 준비 순서 — 엑셀 (0.5b절)

- **요약**: `ingest_excel_data.py`가 엑셀 3종을 받아 "행·절차 읽기, 키워드 6개 추출, 80~90% 샘플링" 방식으로 청크 JSON을 만든다고 적혀 있다.
- **상호참조 검증 — 중요**: 이 절의 설명은 GUIDE_9 0.4절에서 **명시적으로 폐기**된 옛 설계다. GUIDE_9 0.4절은 "이번에 고친 것: 옛 버전은 '행·절차 읽기, 키워드 6개 추출, 80~90% 샘플링'이라고 돼 있었는데, 실제 파일은 시트 단위 서식 문서라 행도 없고 샘플링도 안 한다(1.2절에서 실제 파일로 확인)"라고 직접 이 문구를 인용하며 뒤집었다.
- **발견한 점**: GUIDE_8 1.3절은 GUIDE_5의 옛 그림을 "확정"으로 그대로 옮긴 것이라고 선언돼 있지만, 그 "확정"의 근거였던 GUIDE_5 자체가 나중에(GUIDE_9에서) 사실과 다른 것으로 판명됐다. 즉 GUIDE_8 1.3절은 지금 시점에서는 **낡은 내용**이다 — GUIDE_8 원본을 고치라는 뜻은 아니지만, 이 절만 읽으면 오해할 수 있다는 점은 기록해 둔다.

### 1.4 질문 한 건의 실행 순서 (0.6절)

- **요약**: `POST /ask`·`POST /search` 동시 호출 → `is_followup`/`choose_document_type`/`choose_lang`/`requested_kind` 판정 → SQL 필터+코사인거리 검색 → `rank_manual` 상위 3개 → 답 JSON.
- **핵심 이름**: `is_followup`, `choose_document_type`, `choose_lang`, `requested_kind`, `rank_manual`.
- **상호참조 검증**: GUIDE_9 0.5절의 동일 시퀀스와 거의 같다. 다만 GUIDE_9 0.5절은 "질의어가 equipment 값에 그대로 포함되는지 확인(1.2절 — 사전 배열 아님)"이라는 메시지가 추가돼 있어 엑셀 하드 필터 로직이 더 구체화된 버전이다. 4개 판정 함수 이름(`is_followup` 등)은 GUIDE_12 4절의 질의 처리 함수표와도 정확히 일치한다.

### 2. 그림·표 구현 아키텍처 (GUIDE_6 3.5절)

- **요약**: 본문(text) 쪽은 PyMuPDF 추출→한글 비율 판정, 그림·표 쪽은 영역 탐지→겹침검사→읽기범위 확정→OCR/VLM 폴백을 거쳐 전부 VLM 1차 검증 후 QA 대기열로 들어가는 flowchart.
- **핵심 수치**: 그림 "80pt 이상", 표 "가로선 4·세로선 2".
- **확정/제안 구분**: 문서 서두 선언대로 확정(GUIDE_6 원본 그림).
- **수치 일치 여부 / 발견한 점**: GUIDE_9 0.6절·GUIDE_10 7절·GUIDE_12 1절은 모두 그림 기준을 **"80×80pt 이상(가로·세로 둘 다) 또는 드로잉 40개 이상"**으로 적는데, 이 절의 그림 라벨은 "그림 80pt 이상"이라고만 돼 있어 (a) 가로·세로 둘 다인지 단일 수치인지 불명확하고 (b) "드로잉 40개 이상" 경로(벡터 도형 그림 탐지, GUIDE_10 ⑬번 해결책)가 빠져 있다. 날짜상 GUIDE_8·GUIDE_9가 모두 2026-10-12 작성이라 작성 시점 차이인지, GUIDE_8이 GUIDE_6의 더 이전 버전 그림을 그대로 옮긴 것인지는 문서만으로는 알 수 없다 — 사실 자체만 기록.

### 3. 신규 요구사항 아키텍처 (GUIDE_7 기반, 초안)

- **요약**: GUIDE_7에 글로만 있던 신규 프로덕션 요구사항 4가지를 그림으로 옮긴 상위 절. 문서 자체가 "세부 API 경로·인증 방식은 아직 미정, 흐름의 뼈대만"이라고 못박고 있다.
- **확정/제안 구분**: **초안**(문서 선언).

### 3.1 전체 시스템 구조도 (GUIDE_7 4.1·4.9절 기반)

- **요약**: PC 클라이언트가 메인 API 서버로, 장애 시 예비 API 서버로 붙는 구조. 메인·예비가 같은 DB·GITC·파일 저장소를 공유하는 것으로 "가정"하고 그렸다.
- **확정/제안 구분**: **확인 필요**(문서 내 명시) — "DB·파일 저장소를 메인·예비가 공유하는지, 각자 따로 두고 동기화하는지는 GUIDE_7 4.9절에서도 미정".
- **상호참조 검증**: 같은 미정 사항이 GUIDE_9 3.1절("메인·예비가 이 DB를 공유하면 위 스키마 그대로...")과 GUIDE_9 3.9절("보고서와 파일" 행, "3.1절과의 관계")에서도 반복해서 확인 필요로 남아 있다 — 세 군데 모두 서로 모순 없이 동일한 미정 상태를 가리킨다.

### 3.2 PC별 대화 구분 흐름 (GUIDE_7 4.2절 기반)

- **요약**: PC가 설치ID로 최초 등록하면 자격증명을 발급받고, 재실행 시 같은 식별자로 기존 대화를 이어 조회하는 시퀀스.
- **확정/제안 구분**: **확인 필요**(문서 내 명시) — "식별자"가 설치 ID인지 네이티브 인증서인지 AI 팀 회신 대기 중.
- **상호참조 검증**: GUIDE_9 3.1절의 `pc_identity.install_id` 스키마 설계, 그리고 같은 절의 "확인 필요: install_id 발급 방식(설치 ID vs 네이티브 인증서, AI 팀 회신 대기)" 문구와 정확히 같은 미정 사항을 가리킨다. 모순 없음.

### 3.3 메인/예비 전환 흐름 (GUIDE_7 4.9절 기반)

- **요약**: 메인 운영 중 → 장애 감지 → 예비로 전환 → 메인 신호 복귀 시 복귀 판단, 양쪽 장애 시 서비스 불가로 가는 상태 전이도.
- **확정/제안 구분**: **확인 필요**(문서 내 명시) — 장애 감지·메인 복귀 판정 기준이 GUIDE_7 4.9절에서 전부 미정.
- **상호참조 검증**: GUIDE_9 3.9절 "메인/예비 전환" 절의 확인 항목표(접속구조·전환주체·장애판정·인증과 식별·진행중 질문·보고서와 파일·예비 준비상태·메인 복구·양쪽 장애·시험 방법 10개 행)가 이 그림의 상태들을 훨씬 세분화해 다루고 있어, 서로 어긋나지 않고 GUIDE_9가 후속 심화판이다.

### 3.4 보고서 작성·저장·엑셀생성 흐름 (GUIDE_7 4.6절 기반)

- **요약**: PC가 보고서 내용을 전송→저장→버전ID 발급→엑셀 생성 요청→서식 반영·사진 삽입→다운로드까지의 시퀀스. 검색(pgvector) 반영 단계는 의도적으로 빼고 그렸다.
- **확정/제안 구분**: **확인 필요**(문서 내 명시) — "저장"과 "검색(pgvector) 반영"이 같은 요청에서 같이 일어나는지는 GUIDE_7 6번 절(남은 작업 4번)에서 미정.
- **상호참조 검증**: GUIDE_9 3.2절에도 동일한 문구로 "확인 필요: ... '저장'과 '검색(pgvector) 반영'이 같은 요청에서 같이 일어나는지"가 반복된다. GUIDE_9 3.7절은 한 단계 더 나가 "저장 성공과 'AI 검색 반영·미리보기·엑셀 생성 완료'는 서로 다른 상태로 구분한다"고 방향을 제시한다 — 세 문서가 같은 미정 사안을 일관되게 가리키고 있어 모순은 없다.

### 4. 1차 데모 범위

- **요약**: 전체 프로덕션(3번 절)이 데모에는 전부 필요하지 않다고 선언하고, 기존 1~3번 절은 그대로 둔 채 데모는 이 4번 절 기준으로만 간다고 범위를 다시 잡는 상위 절.
- **확정/제안 구분**: 이 절 산하 내용은 "기존 설계 재사용만으로 바로 구현 가능한 수준"이라고 선언돼 있어 실질적으로 확정에 가까운 범위 정의다.

### 4.1 데이터 현황

- **요약**: 매뉴얼 원본 2종은 준비됨/검색대상, 번역본 2종은 "미준비 — 파일 자체가 없음"으로, 작업지시서·고장수리내역 엑셀은 회사로부터 수령 완료로 적혀 있다.
- **핵심 이름**: `manual_1_ko`(B-64484KO-2, 395쪽), `manual_1_en`(B-63874EN-2, MANUAL GUIDE i), `manual_2_en`, `manual_2_ko`.
- **상호참조 검증 / 발견한 점 — 중요**: 이 절은 GUIDE_8 작성일(2026-10-12) 기준으로 번역본 2종을 **"파일 자체가 없음"**이라고 적고 있다. 그런데 GUIDE_9 1.1절은 "2026-10-13, 파일 입고·짝 검증 완료"라고 기록하고 있어, 번역본 파일 입고는 GUIDE_8 작성 **다음 날** 일어난 사건이다. 이는 GUIDE_8의 오류가 아니라 시점 차이(GUIDE_8이 더 먼저 쓰인 문서)이지만, GUIDE_8만 읽으면 "번역본이 영구히 없다"로 오해할 수 있어 짚어 둔다. 사용자가 전제로 제시한 "이미 확정된 사실"과도 일치(번역본은 2026-10-13에 입고·검증됨).
- **수치 일치 여부**: 395쪽(한글 원본)은 GUIDE_9 1.1·3.13절, GUIDE_10 3절과 동일하게 일치한다.

### 4.2 탭 구성 (3개)

- **요약**: 매뉴얼/작업지시서/고장수리내역 3탭을 `document_type` 값(`manual`/`work_standard`/`repair_log`)으로 구분하며, GUIDE_5 5.2절의 기존 필드를 재사용한다고 밝힌다.
- **상호참조 검증**: GUIDE_9 1.6절 "탭 구성(3개, 확정)" 표와 값·순서가 완전히 동일하다. GUIDE_9 3.1절의 `conversations.document_type` 컬럼 설계도 같은 3값을 그대로 쓴다. 세 군데 모두 일치.

### 4.3 데모용 API (최소 구성, 기존 라우트 재사용)

- **요약**: `GET /`, `POST /ask`, `POST /search`, `GET /manuals/{name}.pdf`, `GET /filters` 5개 라우트만으로 데모가 충분하다고 선언.
- **상호참조 검증**: GUIDE_9 1.1절의 "API 라우트 — 질의" 행이 정확히 같은 5개 라우트를 나열한다. 다만 GUIDE_9는 이후(1.2·1.6절, GUIDE_13 영향) `GET /repair-logs/{chunk_id}.pdf`(원본 시트 보기)와 `GET /qa`·`GET /qa/pending`·`POST /qa/review`(검수) 라우트를 추가로 확정했다 — GUIDE_8 4.3절 작성 시점에는 아직 없던 라우트들이다. 모순이 아니라 범위 확장이다.

### 1.1 구현 대상 현황 (실제로 있는 것 vs 새로 만들 것)

- **상호참조 검증**: "753이 두 번 나오는 건 오타가 아니다" 설명은 문서가 스스로 혼동 가능성을 짚어 해소한 사례다 — `manual_1_ko`의 **청크 753개**와 `manual_2_ko`의 **753쪽**은 서로 다른 파일의 우연히 같은 숫자라고 명시적으로 구분하고 있다. 사용자가 제시한 "395쪽/543쪽" 전제와도 정확히 일치(395쪽=manual_1_ko, 543쪽=manual_1_en).
- **수치 일치 여부**: 753+1,595=2,348 산술이 맞다. 이 2,348이라는 합계는 GUIDE_10에서 별도로 재언급되지는 않지만(GUIDE_10 3절은 "청크 수(753개/1,595개, 합계 2,348개)"로 동일하게 기재) 서로 다른 값으로 어긋나는 곳은 없다.
- **발견한 점**: "`/ask` 응답의 `offers` 필드" 행에는 "수리이력 답에는 `offers.related_repairs[]`를 붙인다"고 적혀 있는데, 바로 이 절 뒤쪽의 "응답 예시" JSON(`{"answer":..., "sources":[161], "model_used":..., "offers":{"figure":[],"table":[]}}`)과 GUIDE_12 6절의 `AskResponse` 데이터 모양(`offers={figure:[], table:[]}`) 어디에도 `related_repairs` 필드가 실제로 나타나지 않는다. 매뉴얼 사례 예시만 보여준 것일 수도 있어 단정적 오류는 아니지만, 수리이력 응답의 구체적 예시가 문서 전체에 한 번도 등장하지 않는다는 점은 기록해 둔다.

### 1.2 엑셀 파싱 — 실제 파일 구조 기준

- **요약**: 세 엑셀 파일 모두 "시트 단위 서식 문서"(시트 1개=레코드 1개)임을 실제로 열어 확인했다고 선언하고, 설비 수리 보고서(40시트)·작업표준서 2종(2시트+1시트)의 고정 라벨을 나열. 라벨 기반 파싱 절차와 "원본 시트 통째로 보여주기"(GUIDE_13 방식 C) 반영을 포함.
- **핵심 이름**: `보고일자`·`장 비 명`·`이상부위`·`고장현상 및 고장원인`·`조치내용 및 대책방안`·`작업구분`; `공정순서`·`작 업 조 건`; 출력 `poc_parsing/repair_logs.json`(`repair_log_s{순번:02d}`), `work_standard_mct.json`, `work_standard_tools.json`.
- **확정/제안 구분**: "실제로 파일을 열어 확인한 결과"라고 명시돼 **확정**(이번 세션 검증). 6번의 "확인 필요: 엑셀 시트를 서식 그대로 PDF로 변환하는 도구... GUIDE_13 6절"은 **확인 필요**로 명시.

### 2부. 다국어 지원 — 작업지시서·고장수리내역

- **요약**: 지원 언어 5개(한국어 원문·영어·일본어·중국어·베트남어)를 선언하고, 엑셀 원본은 번역본 파일이 필요 없어 매뉴얼의 "번역본 없음" 문제와 무관하다고 설명하는 상위 절.
- **상호참조 검증**: "GUIDE_6 4.1절" 참조는 분석 대상 문서 밖이라 직접 대조 불가(참고만).

### 2.1 원칙 — 전부 미리 번역하지 않는다

- **요약**: 고정 사전 항목(설비명·작업구분 등)은 번역 표 1회 작성으로 즉시 변환, 자유 문장(고장현상·조치내용)은 조회 시점에만 번역+캐시하는 2분기 원칙. 검색 로직은 한국어 기준으로 유지.
- **상호참조 검증**: "하드 필터 방식(1.4절 '하드 필터' 기준과 동일)"이라는 참조가 있는데, GUIDE_9 본문에는 "1.4절"이 "데모 완료 기준"(합격 조건표)이라 하드 필터 기준의 원 출처는 사실 0.5절이다. 즉 이 참조는 절 번호가 어긋나 있다 — 0.5절을 가리켜야 할 자리에 1.4절이라고 적힌 것으로 보인다(1.4절 표에도 "하드 필터" 행이 있어 틀린 참조는 아니지만, 정의 자체는 0.5절에 먼저 나온다).

### 2.2 고정 사전 번역

- **요약**: 진동/교체 등 2개 확정 예시와, 1.2절에서 실제 확인한 `작업구분` 값 중 일부(수리의뢰·수리 검토·수리 완료·보수)에 대한 영어·베트남어 "초안" 번역표.
- **확정/제안 구분**: "번역값은 아직 확인된 게 아니라 초안"이라고 명시 — **초안/확인 필요**(담당자 검토 전).
- **상호참조 검증**: "실제 파일의 `작업구분` 칸에는 이 4개 외에도 `수리 확인`, `교체 진행`, `부품 교체`, `교체 예정`, `교체 수리` 등 더 있다"는 서술은 1.2절의 "작업구분 같은 값은... 실제 쓰인 값을 그대로 쓴다"는 설계와 일치한다.

### 2.3 자유 문장 번역 — 지연 + 캐시

- **요약**: 고장현상·조치내용은 첫 조회 시 1회만 번역해 같은 행(`text_i18n`)에 저장, 이후 캐시 재사용. 번역 프롬프트는 "숫자·설비명·날짜·코드는 그대로, 문장만 번역, 없는 내용 추가 금지"로 제한.
- **상호참조 검증**: 이 프롬프트 제한 문구는 GUIDE_10 1.1절 ⑩("번역이 숫자·설비명을 바꿔버림... 프롬프트 제한을 반드시 건다(GUIDE_9 2.3절)")이 정확히 이 절을 가리키며 내용도 일치. `ALTER TABLE manual_chunks ADD COLUMN text_i18n JSONB DEFAULT '{}'`는 0.2절의 `text_i18n JSONB DEFAULT '{}'` 컬럼과 일치(0.2절에선 이미 초기 스키마에 포함돼 있는데, 이 절에서 다시 `ALTER TABLE`로 추가하는 것처럼 적어 약간 중복처럼 보이지만, 0.2절이 최종 스키마를 보여주고 2.3절이 그 컬럼이 왜 필요한지 설명하는 것으로 읽을 수 있어 모순은 아니다).

### 3.2 보고서 작성·저장

- **요약**: 지금 없는 쓰기 API(보고서 작성·수정·저장, 사진 삽입, 엑셀 생성)를 위한 `reports`/`report_photos` 스키마.
- **상호참조 검증**: GUIDE_8 3.4절 흐름도(보고서 작성·저장·엑셀생성)의 PC→서버 흐름을 스키마로 구체화한 것. "확인 필요: ... 저장과 검색(pgvector) 반영이 같은 요청에서 같이 일어나는지"는 GUIDE_8 3.4절과 동일한 미정.

### 3.3 매뉴얼 AI·수리이력 AI 응답 계약

- **요약**: 매뉴얼 AI는 출처(문서·버전·절/페이지)를 내고, 수리이력 AI는 자연어로 설비·고장현상을 해석해 조치 설명+유사 사례 목록을 낸다는 응답 계약. "다른 설비 유사 사례를 보여줄 때는 실제 설비를 표시하고 단정하지 않는다"는 원칙 포함.
- **상호참조 검증**: 이 절은 "다른 설비의 유사 사례를 보여줄 때는..."이라고 **유사 사례 제시를 전제로** 서술하고 있다. 그런데 사용자가 전제로 제시한 사실과 GUIDE_13 2절·GUIDE_9 1.5절 13번 시나리오는 "설비명은 있는데 그 설비 사례가 없을 때 다른 설비 사례를 유사목록으로 보여주는 기능"을 **데모 범위에서 철회**했다고 명시한다. 이 절(3.3절) 자체는 "3부 프로덕션"에서 다시 고려한다고 GUIDE_13 2절에 적혀 있어("3부 프로덕션에서 경고 UI 등을 신중히 설계한 뒤 다시 고려한다(3부 3.3절)") 모순은 아니고, 정확히 이 3.3절이 그 "다시 고려"할 자리로 지정돼 있다 — 상호참조는 일치. 다만 이 절의 현재 서술은 아직 "다른 설비 유사 사례 표시"를 전제로 쓰여 있어, 데모에서 철회된 안전 판단(13번 시나리오의 `NOT_FOUND` 처리)을 프로덕션에서 그대로 쓸지, 더 신중한 설계로 바꿀지는 아직 이 절 안에서 결론이 나 있지 않다(확인 필요 상태로 남아 있음을 기록).

### 3.4 한국어·영어 AI 답변 처리

- **요약**: 매뉴얼 AI 답변 언어를 정하는 3가지 검토안(프로그램 언어 설정 전달/AI 자체 판정/조합)과, 번역 짝 자체는 3.13절 검증으로 "일부 해소"됐다는 갱신, B군(선반+MC 공통 vs MC 전용) 범위 차이로 인한 "자료 없음" 처리 원칙.
- **상호참조 검증**: "일부 해소(2026-10-13): ... 3.13절"이 가리키는 3.13절 내용(A군/B군 검증)과 정확히 일치. "B군은 한글판이 선반+MC 공통, 영어판이 MC 전용"은 3.13절 표의 비고("KO는 선반+MC 공통, EN은 MC 전용으로 보임")와 완전히 일치하며, 사용자가 전제로 제시한 사실(manual_2_ko가 선반+MC 공통이라 범위가 더 넓다)과도 일치한다.
- **발견한 점**: "확인 필요로 남은 것"에 `text_source`(기계번역/공식번역 구분) 제안이 처음 등장하는데, 이 컬럼명은 3.13절의 스키마 확장 표에 `text_source` 컬럼(`original`/`official`/`mt`/`mt_reviewed`)으로 실제로 반영돼 있어 두 절이 정확히 연결된다.

### 3.5 기존 수리 자료 이관 및 문서 열람

### 3.13 manual_chunks 스키마 확장 — 두 문서군 정렬(align) 설계 (제안)

- **요약**: 2026-10-13 `pdftotext` 직접 검증으로 매뉴얼 PDF가 번호(`manual_1`/`manual_2`)가 아니라 문서번호(B-64484/B-63874)로 묶이는 두 문서군임을 확정하고, 이를 근거로 `doc_id`/`align_key`/`section_no`/`anchors` 등 컬럼 추가와 `chunk_alignments` 테이블을 제안하는 절.
- **핵심 이름·수치**: A군(B-64484): `manual_1_ko` 395쪽 ↔ `manual_2_en` 434쪽. B군(B-63874): `manual_2_ko` 753쪽 ↔ `manual_1_en` 543쪽. 신규 컬럼 `doc_id`·`align_key`·`section_no`·`section_path`·`page_start`/`page_end`·`model`·`machine_type`·`text_source`·`anchors`·`embed_text`·`source_hash`·`updated_at`. `chunk_alignments(align_key, ko_chunk_id, en_chunk_id, unit, pair_type, score, status, method)`. `score>=0.8`→`auto`, `0.5~0.8`→`review`.
- **확정/제안 구분**: 문서번호·쪽수 검증 자체는 "**검증 결과**(2026-10-13, 실제 4개 PDF를 직접 열어 확인)"로 **확정**. 스키마 확장·`chunk_alignments`·마이그레이션 설계 전체는 "**(제안)**"으로 명시. G코드·알람 일치율 등 세부 수치는 "사용자 제공... 이 세션에서 직접 재검증하지 않음"이라고 스스로 신뢰 수준을 낮춰 표시.
- **수치 일치 여부**: 이 절의 395/434/543/753쪽 표는 1.1절의 동일 수치와 완전히 일치한다. 사용자가 이번 작업의 전제로 제시한 "manual_1_ko(B-64484KO,395쪽)↔manual_2_en(B-64484EN,434쪽)" 및 "manual_1_en(B-63874EN,543쪽)↔manual_2_ko(B-63874KO,753쪽, 선반+MC공통이라 범위 더 넓음)"과 정확히 일치한다.
- **상호참조 검증**: "1.1절의 '번역본' 방향 설명은 맞다"는 자기참조가 실제로 1.1절 표의 방향(한글→영어 번역본=`manual_2_en`, 영어→한글 번역본=`manual_2_ko`)과 일치한다. GUIDE_10 ⑰ 행의 설명과도 완전히 일치. GUIDE_9 1.6절의 "주의 — 버튼을 단순 '언어 전환'으로 표기하지 않는다"가 이 절을 근거로 들고 있는 것도 내용상 정확하다.
- **발견한 점**: `chunk_id` 규칙 변경에서 "기존 적재분이 있으면 구id→신id 매핑 테이블로 마이그레이션한다"고 적혀 있는데, 이 저장소는 백지 상태(전제 8)라 사실 "기존 적재분" 자체가 아직 존재하지 않는다 — 이 문구는 향후(데모 적재 이후 프로덕션 전환 시점)를 가정한 서술로 보이며, 지금 시점에는 해당하지 않는다는 점을 짚어 둔다(오류는 아니고 시점 전제가 묵시적으로 다름).

### 3.14 이 문서의 한계

- **요약**: 0부 그림은 GUIDE_6 설계를 그대로 그린 것, 1부는 실제 파일 확인했지만 서버 미검증, 2부 번역값은 초안, 3부는 전체가 AI 팀 회신 대기 초안이라고 스스로 한계를 정리. "포트·경로·수치 기준값은 이 문서에 없다 — GUIDE_10을 본다"는 역할 분리 재확인. 마지막 표에서 "문서를 더 써서 채워지는 게 아닌 것" 4가지(GITC 요청형식, VLM 서비스, 표 탐지 정확도, 엣지케이스)를 정리.
- **상호참조 검증**: "포트·경로·수치 기준값은... GUIDE_10을 본다"는 선언이 실제로 GUIDE_10의 2~7절 구성(포트·경로·체크리스트·DB컬럼·HTTP코드·모델·수치)과 정확히 맞아떨어진다 — 역할 분리가 실제로 지켜졌다.

### 1. 전체 흐름과 문제 발생 지점

- **요약**: 입력(PDF·엑셀)부터 답변까지 전체 파이프라인을 번호(①~⑰, 아래 1.1절 표의 행 번호와 동일)와 함께 한 장으로 합친 flowchart. "이번에 고친 것" 설명으로, 그림·표 bbox 탐지가 "본문이 깨졌을 때만"이 아니라 청킹 단계부터 본문과 그림·표가 처음부터 두 갈래로 갈라진다고 수정.

- **발견한 점(문서 전체에 해당)**: 서두와 4번 규칙 두 군데에서 **"GUIDE_9·10·11"**이라고 세 문서를 나란히 언급한다. 그런데 이번 작업의 배경 지식대로 GUIDE_11.md는 한때 만들어졌다가 삭제되어 지금 저장소에 존재하지 않는다.
