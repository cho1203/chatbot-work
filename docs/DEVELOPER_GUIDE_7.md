## 핵심 요약 (먼저 읽기)

개발 들어가기 전에 전체 그림만 보는 절이다. 자세한 내용은 0번부터 순서대로 본다.

**지금 있는 것 (GUIDE_5·6)**

| 영역 | 상태 |
|---|---|
| 매뉴얼·수리이력 AI 질문·답변 | 있음 (질의 라우팅 → 검색 → 생성) |
| 그림·표 표시 | 있음, 단 승인된 것만 검색에 반영 (QA 게이트) |
| 엑셀 다국어(5개 언어) | 설계만 있음, 구현 전 |
| 대화 저장 | **없음** — 브라우저가 매번 직전 질문만 같이 보냄 |
| 스트리밍(SSE) | **없음** — 질문 한 번에 답 한 번 |
| 서버 이중화 | **없음** — 단일 프로세스 하나만 돌아감 |
| 쓰기 API(작성·수정·삭제) | **없음** — 조회만 가능 |

**새로 요청받은 것 (챗봇·서버 쪽)**

| 영역 | 요청 내용 |
|---|---|
| PC별 대화 구분 | 설치 ID 등으로 PC마다 대화를 나눠서 서버에 저장·조회 |
| 메인/예비 GPU | 장애 시 자동 또는 수동으로 예비 서버로 전환 |
| 보고서 작성·저장·엑셀 생성 | PC에서 보고서를 쓰고 저장한 뒤, 엑셀 서식 파일로 뽑아서 다운로드 |
| API 정보 | 메인·예비 각각의 주소·경로·인증 방식 회신 |

**가장 먼저 결정해야 하는 충돌 4가지**

지금 설계 원칙과 이번 요청이 정반대인 부분이다. 기능을 "추가"하는 게 아니라 전제를 "바꿔야" 하므로 제일 먼저 방향을 정해야 한다.

1. 서버가 대화를 저장하지 않는다 ↔ PC별로 서버에 저장·조회해야 한다
2. 스트리밍이 없다 ↔ SSE로 진행 상태를 보내야 한다
3. 서버가 하나다 ↔ 메인·예비 두 대가 돌아가야 한다
4. 쓰기 API가 없다 ↔ 보고서를 쓰고 저장하는 API가 있어야 한다

**다음에 할 일 순서**: 6번 절("남은 작업") 참고.

## 0. 이 문서의 성격

삼광 통합 프로그램 쪽에서 AI 백엔드(이 프로젝트)에 보낸 업무 요청서를 기준으로, 챗봇·서버가 실제로 구현해야 하는 부분만 정리한다. 두 가지를 섞지 않고 구분한다.

- **기존 기능 연동**: 지금 설계(GUIDE_5·6)에 이미 있는 것을 클라이언트 프로그램에 연결하는 것
- **추가 요청사항**: 지금 설계에 없는 것(보고서 작성·저장·엑셀 생성, 메인/예비 GPU 이중화, PC별 대화 구분, 서버 측 대화 영속 저장 등)을 새로 만드는 것

5번 절에서 요청서의 각 항목을 기존 설계와 대조해, 뭐가 이미 있고 뭐가 새로 필요한지 표로 정리한다.

## 1. 기존 구현 요약 (GUIDE_5 기준)

| 항목 | 현재 상태 |
|---|---|
| 벡터 저장소 | PostgreSQL + pgvector, `manual_chunks` 테이블 (FAISS에서 전환함) |
| 임베딩 | bge-m3 (`SentenceTransformer`), 정규화 벡터 |
| 생성 모델 | GITC(`hyperclovax-seed-32b`)로만 쓰기로 확정, 로컬 대체 없음 |
| 색인 대상 | PDF 매뉴얼 2종(한글·영어 원본), 엑셀 3종(수리 보고서·작업표준서 2개) — **3번 절의 신규 매핑표와 같은 파일인지 확인 필요** |
| 서버 구성 | `venv` 단일 프로세스, 포트 8155, **이중화 없음** |
| 대화 저장 | **서버 측 영속 저장 없음** — 브라우저가 매 요청마다 `prior_query`만 전달 |
| 응답 방식 | `/ask`·`/search`를 `Promise.allSettled`로 동시 호출, **스트리밍(SSE) 없음** |
| 쓰기 API | 업로드·재학습·삭제·수정 API 없음 — 색인은 관리자가 스크립트로만 실행 |
| 문서 다운로드 | PDF는 `GET /manuals/{name}.pdf`로 서빙. 엑셀 원본 다운로드는 설계에 명시 안 됨 |
| 인증 | 없음. local(로컬) 바인드 전용 |

## 2. 그림·표 구현 요약 (GUIDE_6 3번)

- 그림·표는 bbox로 위치를 찾고, 같은 언어 매뉴얼에 원문 문장이 있으면 그대로 쓰고, 없으면 OCR(EasyOCR → PaddleOCR → VLM 순)로 읽는다. bbox는 위치만 담당하고, VLM은 ① 읽기 폴백, ② QA 진입 전 "캡션이 그림과 맞는가" 1차 검증 두 자리에만 보조로 들어간다(GUIDE_6 3.3.6)
- VLM 호출은 자유 문장이 아니라 구조화된 출력(`text`/`found`/`confidence`)으로 강제하고, temperature를 낮춰 추측·보완을 막는다(GUIDE_6 3.3.7)
- 본문은 조각마다 한글 비율(임시 기준 20%)로 살아있는지 판정해, 살아있으면 그대로 쓰고 깨졌으면 bbox 위치로 OCR을 돌린다.
- 그림·표와 OCR로 채운 본문, VLM이 "불일치"로 판정한 항목은 QA 검수(전수검사, 안전 문구 2차 승인)를 거친 것만 pgvector에 반영된다. VLM 판정은 최종 승인을 대신하지 않는다
- 현재 수치: 그림·표 584건(한글+영어), 그중 567건에 문장이 채워짐. 전부 검수 대기(`pending`) 상태.
- 사진·문서 열람과 직접 관련: 그림은 PNG 파일로, 표는 HTML로 저장되고 `image_path`로 화면에 표시된다. **요청서 2.4·3.2의 "사진 연결·배치·전체 보기"와 바로 연결되는 부분**.
- bbox 좌표(pt 단위, PDF에 이미 있음) → 250dpi로 페이지 렌더링 → `pt × (250÷72 ≈ 3.47)`로 픽셀 좌표 환산 → 그 좌표로 크롭 → OCR·VLM에 전달. 이 계산은 실제 이미지를 만드는 과정이라 bbox "위치 찾기"와 별개 단계다(GUIDE_6 3.3.1)
- 렌더링·크롭·OCR·VLM 호출은 **색인 시점(배치)에서만** 일어난다. `POST /ask`·`POST /search` 호출 경로에는 전혀 나타나지 않는다 — 질문이 들어오면 이미 만들어진 결과(벡터·이미지 파일)만 조회한다(GUIDE_6 3.4)

## 3. 다국어 기능 요약 (GUIDE_6 4번)

- 작업지시서·고장수리내역(엑셀)을 한국어 원문 기준으로 색인하고, 한국어·영어·일본어·중국어·베트남어 5개 언어로 보여주는 설계. **구현 전, 설계만 완료된 상태**.
- 고정 단어(설비명·증상·조치 등)는 번역표로 즉시 변환, 자유 문장은 조회 시점에 GITC(`hyperclovax-seed-32b`, 본문 생성과 같은 모델·API 재사용)로 번역 후 캐시. 다만 번역은 창작이 아니라 그대로 옮기는 작업이라 temperature는 본문 생성(0.2)보다 낮게(0~0.1) 호출해야 한다 — GITC가 이 모델 하나만 제공하는지, 다른 옵션이 있는지는 플랫폼 관리 쪽 확인이 필요하다.
- 검색 로직은 한국어 기준 그대로 유지하고, 번역은 질의 입구(역매핑)와 화면 출구(캐시된 번역)에만 끼워 넣는다.
- 요청서 2.3("한국어·영어 AI 답변 처리")의 "AI 자체 언어 판정" 검토안과 같은 방향이지만, 요청서는 PDF 매뉴얼 언어 처리를 묻고 있고 GUIDE_6 4번은 엑셀(작업지시서·수리이력) 언어 처리를 다룬다 — **대상 자료가 다르다는 점을 구분해야 함**.

**실제 대상 파일 (현장 자료 요청 목록 기준)**

| GUIDE_6 4번에서 부르는 이름 | 실제 자료 | 세부 항목 |
|---|---|---|
| 작업지시서 | 작업표준서(SOP) | 작업순서, 사용도구, 작업조건, 품질기준, 완료조건 |
| 고장수리내역 | 오류·고장 사례 및 조치내역 | 오류 유형, 원인, 조치방법, 소요시간 |

**확인 필요**: "작업표준서(SOP)"·"오류·고장 사례 및 조치내역"이 GUIDE_5(1번 절)에서 이미 쓰던 `설비 수리 보고서.xlsx`·`M3 TN4 DECO 작업표준서_251104.xlsx`와 같은 파일인지, 아니면 별도로 새로 받는 파일인지 확정되지 않았다. 다른 파일이면 GUIDE_5 10.1·10.2절의 열 이름 가정도 새로 맞춰야 한다. 또한 "작업지시서"(GUIDE_6 4번 제목)와 "작업표준서"(SOP)는 원래 다른 개념이다 — 작업지시서는 건별 지시 문서, 작업표준서는 절차 기준 문서. 지금은 같은 것으로 보고 진행 중이라는 점을 개발 전에 다시 확인한다.

**엑셀 처리 — PDF와 다른 점 (GUIDE_5 10장 기준)**

엑셀은 셀에 텍스트가 그대로 들어있어서 3번(그림·표)에서 겪은 폰트 깨짐 문제가 없다. **OCR·bbox·VLM은 필요 없다.** 다만 "그대로 불러오기"는 아니고, 아래 가벼운 처리가 필요하다.

- **행 단위 청킹**: 행(또는 절차) 하나를 청크 하나로 나눈다
- **키워드 추출**: 고정 사전으로 증상·조치 등 6개 키워드를 뽑는다 (10.1절)
- **샘플링**: 전체가 아니라 80~90%만 색인한다
- **열 이름 확인 (선행 필수)**: 지금 설계는 "날짜·설비명·고장증상·조치내용" 같은 열 이름을 가정만 해둔 상태. 실제 파일을 받으면 열 이름이 맞는지부터 확인하고, 다르면 코드를 맞춰 고쳐야 한다 (10.1·10.2절)
- **표 형식 확인**: 특히 작업표준서(SOP)는 셀 병합·다단 헤더가 있을 수 있어 pandas 단순 읽기가 안 통할 수 있다 (10.2절)

## 4. 신규 업무 요청 — 챗봇·서버 쪽 요구사항

### 4.1 업무 범위

| 구분 | 요청 내용 |
|---|---|
| 기존 기능 연동 | 매뉴얼 AI와 수리이력 AI를 별도 기능으로 제공. 자료 범위와 대화 종류 구분 |
| 기존 기능 연동 | 대화 기록을 서버에 저장하고 PC에서 목록·메시지 조회. 로그인 화면 없음 |
| 기존 기능 연동 | 자연어로 수리 사례 검색, 보고서 전체 내용·사진 열람, 원본 엑셀 다운로드. 설비 선택 강제 안 함 |
| 확정된 서버 구성 | 메인 GPU 서버 + 장애 시 예비 GPU 서버. 양쪽 API 주소·경로·인증·전환 정보 요청 |
| 적용 방식 협의 | PC별 대화 구분 방법(설치 ID + 네이티브 인증 제안, AI 팀 기존 방식 있으면 그에 맞춤) |
| 언어 방식 협의 | 프로그램 언어 설정 전달 vs AI 자체 언어 판정 + 번역 매뉴얼 활용, 비교 검토 |
| 추가 요청사항 | PC에서 보고서 작성·수정·서버 저장, 엑셀 서식 파일 생성·다운로드 |

자료 범위별 API 분리가 곧 별도 서버·별도 DB를 뜻하지는 않는다.

### 4.2 PC별 대화 구분 및 기록 조회

필요한 동작: 각 PC가 자신의 대화 목록·메시지를 불러오고, 프로그램을 재실행해도 기존 대화를 이어서 조회.

설치 시 고유 ID를 만들고 서버가 자격 증명을 발급하는 네이티브 PC 인증을 제안하되, 이 방식의 신규 개발이 필수는 아니다. AI 팀에 이미 있는 개별 구분 방식이 있으면 그걸 우선한다.

확인할 사항:
- 구분 단위(물리 PC / 앱 설치 / 서버 발급 식별자 / 세션)
- 로그인 화면 없이 구분 유지 가능 여부
- 최초 연결·재실행·인증 만료 시 PC 동작
- PC 교체·재설치 후 기록 복구
- 같은 PC를 여러 사람이 쓰거나 이미지 복제했을 때 처리
- 다른 PC 대화가 섞이거나 식별값 변경만으로 조회되지 않게 하는 방법
- 메인·예비가 DB를 공유하는지 (공유하면 전환 시 별도 조치 불필요 — 식별자로 같은 DB를 조회하므로 자동 유지됨. 공유하지 않는 경우에만 동기화·복제 설계가 추가로 필요)

요청 제공물: 권장 식별 방식과 이유, 클라이언트 연동 절차, 필요 API, 인증 정보 전달 방식, 기록 유지·복구 규칙, 메인·예비 DB 공유 여부.

### 4.3 매뉴얼 AI와 수리이력 AI

| 기능 | 필요한 서버 동작과 데이터 |
|---|---|
| 매뉴얼 AI | 지정된 두 매뉴얼 답변, 실제 사용한 문서·버전·절/페이지 출처 |
| 수리이력 AI | 설비 선택 없이 자연어 질문 처리, 설비·고장현상·조건 해석, 조치 설명과 유사 사례 목록 |
| 사례 목록 | 보고서 식별자·버전, 제목, 설비 원문, 보고일, 조치 요약, 원본 파일명·시트 참조 |
| 대화 기록 | 대화 생성, 목록·메시지 페이지 조회, 과거 답변과 당시 출처 조회 |
| 실행 상태 | 처리중·완료·실패·취소 확인, 연결 단절 시 접수·결과 확인 |
| 결과 구분 | 자료 없음·확인 질문·검색 준비중·부분 검색 실패·서비스 오류 구분 |

다른 설비의 유사 사례는 실제 사례 설비를 표시하고, 질문 대상의 실제 이력으로 단정하지 않는다. 예정·검토·미상 내용을 완료 조치로 바꾸지 않는다. 매뉴얼 자료와 수리이력 자료를 섞지 않는다.

SSE는 진행 상태 + 저장 후 최종 답변을 전달하는 방식으로 가정하고 있으나, 실제 제공 방식·이벤트 형식·취소/연결 단절/재조회 규칙은 확인이 필요하다.

### 4.4 한국어·영어 AI 답변 처리

| 검토안 | 동작 | 회신 요청 |
|---|---|---|
| 프로그램 언어 설정 전달 | PC가 설정 언어를 보내고 서버가 그 언어로 답변 | 지원 여부, 전달 필드, 질문 언어와 다를 때 동작 |
| AI 자체 언어 판정 | AI가 질문 언어를 판정하고 번역 매뉴얼로 답변 | 판정 기준, 짧은 질문·설비 코드·혼합 언어·번역본 누락 처리 |
| 조합 가능 여부 | 설정 언어를 답변에 적용, AI 판정은 검색 보조 | 적용 가능성, 기존 구조와 차이, 개발 범위 |

두 안은 배타적이지 않다. 한국어·영어 매뉴얼의 준비·검수 상태, 원문·번역본 버전·페이지 연결, 외국어 질문으로 한국어 수리 기록을 찾는 방법을 확인해야 한다. 원문 개정 후 오래된 번역본을 최신으로 안내하면 안 된다.

### 4.5 기존 수리 자료 이관 및 문서 열람

- 제공 파일 전량 보관, 각 시트의 원문·작업/부품 행·사진·보고서를 연결. 시트마다 별도 테이블이나 필수 승인 절차를 만들지 않음
- 검토 대상 workbook 규모: 약 125 MiB, 40개 시트, 51개 작업/부품 행, 44개 그림 배치 (완료 수리 건수와는 다름)
- 분석·검색 준비·실패 상태와 재처리 방법 제공, 동일 파일·시트 재처리로 중복 등록 방지
- PC에는 목록·요약을 먼저 제공하고, 선택한 보고서의 전체 내용·사진을 불러옴. 전체 workbook을 매 질문마다 내려받지 않음
- 전체 보기 형식(PDF·HTML·페이지 이미지 등)은 미확정, 제공 가능한 방식을 검토
- 원본 다운로드 시 파일명·관련 시트 안내. 한 workbook의 여러 시트를 별개 원본 파일로 표시하지 않음
- 원본의 사진·설명·작업 행 연결과 순서를 보존. 사진 표시와 AI의 사진 의미 분석은 별개 — 이미지 분석·OCR 필요 여부는 별도 협의

요청 제공물: 이관 방식과 처리 상태, 파일·시트·사진 연결 구조, 전체 보기·원본 다운로드 API, 실제 자료 열람 샘플.

### 4.6 추가 요청사항 — 보고서 작성과 엑셀 서식 생성

**개발 범위 (전부 신규)**

1. PC에서 기존 보고서 서식에 맞춰 내용 작성
2. 작업/부품 행과 사진을 추가해 서버에 저장
3. 저장한 보고서를 다시 조회·수정
4. 저장된 특정 버전의 내용을 엑셀 서식에 반영해 파일 생성
5. 생성된 엑셀을 PC에서 다운로드

입력 대상: 보고일자·보고자·장비명·모델명·규격/사양·현장명·작업명·이상부위·고장발생일·작업일시·고장현상 및 원인·조치내용 및 대책방안·작업/부품 행·사진. 필수값·입력 제한은 서식과 함께 확정.

AI가 실제 수행하지 않은 수리 내용을 자동 작성하지 않는다 — **GUIDE_5·6 전체에 깔린 "매뉴얼에 없는 내용은 만들지 않는다" 원칙과 같은 방향**. 업로드 원본 엑셀은 그대로 보존하고 신규 작성·수정본은 생성 파일로 구분한다.

**사진 첨부와 서식 배치 — 정할 항목**

| 논의 항목 | 정할 내용 |
|---|---|
| 사진 출처 | 문서에서 추출한 사진 vs PC에서 새로 첨부한 사진 구분 |
| 업로드 | 지원 확장자, 크기·해상도·개수 제한, 업로드 완료·실패 확인 |
| 본문과의 연결 | 보고서 전체 첨부 vs 특정 작업/부품 행·사진 칸 연결 |
| 순서와 설명 | 사진 ID, 표시 순서, 캡션, 작업 전/후 분류 필요 여부 |
| 엑셀 삽입 | 파일 내부 포함(우선 검토) vs 링크 |
| 크기와 위치 | 서식의 사진 칸·셀 범위, 종횡비·회전·잘림, 여백·정렬 |
| 여러 장 처리 | 행 확장 / 별도 시트 / 추가 페이지 |
| 미리보기·인쇄 | 화면 전체 보기와 엑셀 인쇄 결과 일치, 페이지 나눔·가독성 |
| 수정·삭제 | 사진 교체·순서 변경을 새 버전에 반영, 과거 버전과 연결 |
| 오류 처리 | 누락·손상·변환 실패 사진 처리와 사용자 안내 |

배치 확인 샘플: 사진 없음·한 장·여러 장·세로/가로 혼합·긴 캡션·여러 작업 행 포함. **입력 데이터 → 전체 보기 → 생성 엑셀** 순서로 대조.

### 4.7 데이터 저장과 변경 처리

| 데이터 | 필요한 관계와 관리 내용 |
|---|---|
| 대화·메시지·실행·출처 | 개별 구분 방식과 연결, 당시 답변 언어·자료 버전 |
| 원본 파일·시트·보고서 | 파일 하나의 여러 시트와 보고서 관계, 원본 보존 |
| 보고서 본문·작업/부품 행 | 보고서 식별자·현재 버전, 행 순서·입력값 |
| 사진·첨부 | 파일 식별자, 보고서/행 연결, 표시 순서·캡션·배치 정보 |
| 수정 이력 | 본문·행·사진·서식 버전의 당시 상태 |
| 저장 요청 결과 | 응답 유실 시 기존 저장 결과 확인, 중복 등록 방지 |
| 검색·미리보기·엑셀 작업 | 대상 보고서 버전, 준비/성공/실패 상태, 생성 파일 |

저장 성공과 AI 검색 반영·미리보기·엑셀 생성 완료는 구분한다. 저장 후 작업 유실, 옛 버전 작업의 늦은 완료, 같은 보고서 동시 수정, 이미 성공한 저장의 재전송 처리 방식이 필요하다.

### 4.9 메인 GPU와 예비 GPU — 확정된 구성

| 확인 항목 | 회신할 내용 |
|---|---|
| 접속 구조 | 메인·예비 각각의 API 주소·경로 또는 통합 주소에서 환경을 구분하는 방식 |
| 전환 주체 | 서버가 전환하는지, PC가 주소를 선택하는지 |
| 장애 판정 | 메인 불가 판정 기준, 상태·오류 신호, 전환까지 걸리는 시간 |
| 인증과 식별 | 예비 접속 시 기존 인증·개별 구분값·대화 ID 유지 여부 |
| 진행 중 질문 | 메인에서 접수·실행·저장된 요청을 예비에서 확인·이어 처리하는 범위 |
| 보고서와 파일 | 양쪽 경로에서 같은 보고서·사진·원본·생성 파일·버전 조회 방법 |
| 예비 준비 상태 | 모델·자료·언어·용량·기능 호환성, 예비에 없는 기능 목록 |
| 메인 복구 | 복귀 판단·시점, 예비 처리 중인 요청 처리 |
| 양쪽 장애 | 최종 오류와 사용자 안내, 이용 가능한 기능 범위 |
| 시험 방법 | 개발 환경에서 메인 중단·예비 처리·메인 복귀 검증 방법 |

메인 처리 결과가 불명확한 상태에서 예비로 새 요청을 무조건 보내 중복 답변·저장이 발생하면 안 된다. 저장 완료 후 응답만 유실됐다면 기존 결과를 복구하고, 이미 취소·실패로 종결된 요청을 되살리지 않는다. GPU 예비 구성과 DB·원본 파일 백업은 별도 — 백업·복원 절차, 허용 데이터 손실 시간·복구 목표가 필요하다.

### 4.11 챗봇·서버 범위가 아닌 것

로그인 화면, AI의 공식 수리 기록 자동 작성, 오프라인 자동 전송 큐, 필수 승인 절차는 이번 요청에 없음. 화면·입력 폼·파일 다운로드 UI는 서버·API 범위가 아니라 별도로 다룬다.

## 6. 남은 작업 — 제안 순서

1. **PC별 대화 구분 방식 확정** — 지금 "서버 저장 없음" 설계를 뒤집는 가장 근본적인 변경이라, 다른 작업보다 먼저 방향을 정해야 함
2. **서버 측 대화 저장 설계 추가** — 1번이 정해져야 스키마를 잡을 수 있음
